# M57.9 — Pre-release adversarial review

**Depends on:** [M46](m46.md)–[M57](m57.md), and [M51.9](m51.9.md) having
already run.
**Discharges:** nothing on the scope tables; it is the gate [M58](m58.md) closes
behind. [M32.9](m32.9.md) is the specification it runs to.

It runs **before** [M58](m58.md) rather than inside it, because findings are
work, work re-triggers validation, and the documentation pass has to describe a
tree that is finished. That ordering is [workflow.md](../workflow.md)'s, not a
preference.

## Why here, as well as at M51.9

[M51.9](m51.9.md) could not see any of the phase's dangerous work, because none
of it had landed. Everything that changes who can do what — erasure
([M52](m52.md)), a second factor ([M53](m53.md)), a credential that crosses
tenancies ([M54](m54.md)) — plus the phase's only new outbound connection
([M55](m55.md)) and its deployment claims ([M56](m56.md), [M57](m57.md)) all sit
above it.

**[M54](m54.md) is the single strongest reason this review is budgeted.** It
re-derives four recorded decisions at once — F103's read bound, M44's
`ResolveWorkspaceForUser` parameter, D43's role cap, D87's rotation rule — and
its failure mode is a key resolving into an organization it should not reach,
which no test catches unless the test was written to look for it. That is a
second reader's job.

## Done means

- M46 through M57 re-read against their claims, with M51.9's findings confirmed
  as actually fixed rather than assumed.
- Multi-dimension and adversarially verified, per M32.9. Only confirmed findings
  are reported.
- **Verified live rather than by test**, on the reasoning Phase 1's M19
  established — standing up a fresh instance and using it reaches bugs that
  reading code against its own intent does not:
  - a fresh instance set up from scratch, exercising signup, invite, team,
    workspace and organization creation end to end against the redesigned
    interface;
  - **an upgrade from 0.2.0 to this build**, confirming migrations are additive,
    that no configuration became silently required, and specifically that an API
    key issued under 0.2.0 resolves to the same identity afterwards — M54's own
    assertion, checked against a real upgraded database rather than a fresh one;
  - the second factor enrolled, used, disabled, and recovered with a recovery
    code, on a real authenticator rather than a test vector;
  - an account deleted and its residue read back: audit entries still
    correlating, the address gone, the dispute row still readable;
  - the redirect SLO re-measured on the **final** build, not an intermediate
    one.
- **The single-instance conformance test from [M57](m57.md) is confirmed to
  actually constrain something** — sabotaged by making a dependency required,
  confirmed failing, restored by counter-edit. A guarantee nobody has seen fail
  is a guarantee nobody has tested.
- Every in-spec finding is fixed; every out-of-spec one lands in
  [deferred-findings.md](../deferred-findings.md) for the owner review
  [M58](m58.md) then acts on.
- Anything the review changes re-triggers validation from the top.

## Risks

The temptation at this point is to treat the review as a formality standing
between a finished phase and a release. Phase 1's second review found seven
findings that blocked a tag on a branch that felt done, and Phase 2's two reviews
found defects *no single milestone's definition of done could catch, because each
milestone was internally consistent*. This phase has three milestones whose
correctness is only visible across seams — M52's erasure against M54's key
resolution against M53's session mint — and that is exactly the shape those
reviews were describing.

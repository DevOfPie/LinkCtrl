# M67 — Runtime lifecycle: an add-on arrives and leaves without a reboot

**Depends on:** [M60](m60.md) *(the loader and verification it drives)*,
[M62](m62.md) *(grants are resolved at activation)*, [M63](m63.md) *(removal
is what creates an orphan)*, [M66.5](m66.5.md) *(hard, added 2026-08-23 — removal
has a pool to drain, and the bullet below is unsatisfiable without one)*.
**Discharges:** the install/remove halves of the owner's Add-on manager answer
([phase-4-candidates.md](../phase-4-candidates.md#the-add-on-manager-is-a-real-surface-not-a-settings-page)).
Split from the manager surface at the plan's review, 2026-08-18 — the M50.5/M50.6
precedent: an upload surface and the thing it feeds are two reviewable units,
and this is the one whose Risks called it the sharpest permission the UI has
ever offered.

M60's lifecycle is a directory read at boot. This milestone makes arrival and
departure runtime acts: a module is installed, verified, activated, and removed
without restarting the instance — the mechanism [M68](m68.md)'s page will
drive, built and reviewed on its own before a page makes it two clicks.

## Done means

- **The permission exists before the surface**: `addons.manage`, an
  instance-principal scope in the D98 pattern — enumerated, **seeded by an
  insert-and-grant migration** (the 00800 pattern; `03400_instance_principal.sql`
  is the instance-scope precedent), and non-delegable to API keys. The
  milestone records its D18 limb per the inherited rule; the working argument
  is the second limb — a key that can add executable capability has widened
  its own reach past any scope it was issued with.
- **Install is an upload, never a fetch**: a `.wasm` + manifest pair arrives
  in the request body, runs M60's checksum verification and manifest parsing
  before anything activates, and **nothing is fetched from a URL** — a fetch
  would be the SSRF-shaped convenience this product refuses everywhere else,
  and its absence is deliberate. The operator's boot-directory route from M60
  keeps working unchanged.
- **Activation is atomic with the stored state**: the file set and the
  manifest record move together, so a crash mid-install leaves either the old
  world or the new one, never a half — asserted by a test that kills the
  sequence between steps.
- **Removal unloads without a reboot**, and the unload semantics are this
  milestone's design work stated in its diff: in-flight invocations complete
  or are interrupted (chosen and recorded), held instances are released, and
  the leak risk is bounded by test — repeated install/remove cycles hold
  resident memory flat within a stated tolerance.
- **Removal drains the add-on's pool** ([M66.5](m66.5.md)'s seam, written into
  this file when that milestone was added on 2026-08-23 so it is owned rather
  than discovered). M66.5 keeps instances rather than destroying them, so
  unloading has something to release that M66 did not have: pooled instances
  for the removed add-on are drained before the module is closed, and a test
  drives install → pool warm → remove and asserts nothing of that add-on
  survives. If M66.5's design turns out to make this free, say so here rather
  than dropping the bullet.
- **A removed `required` add-on cannot brick the boot it was required for**:
  removal updates the stored state atomically with the file set, so the next
  boot does not stop for a module the operator deliberately removed. Tested.
- **Every lifecycle act is audited**: `addon.installed`, `addon.removed`,
  each naming the module, version and checksum, through the M21 writer.
- **The API is the mechanism** (inherited rule): install and remove land in
  `api/openapi.yaml` under `addons.manage`, replayed by the contract test —
  [M68](m68.md)'s page calls what this milestone ships, and has no private
  side door.
- **The single-instance gate re-runs against a lifecycle sequence**: M60's
  add-on case grows install-then-remove-then-serve, so *one container is a
  tested configuration* covers the moving version of the claim, not only the
  boot-time one.
- **Deliberately not done:** any page (M68); purge of an add-on's schema —
  removal leaves the orphan M63 makes enumerable, and offering the purge
  choice is the surface's job at the point of decision; upgrade-in-place
  (remove-then-install is the path this phase ships, and a one-step upgrade
  with migration implications is its own future argument).

## Risks

- Upload-a-binary over HTTP is the risk the split isolated: the scope gate,
  the checksum check and the audit record are all load-bearing, and
  `docs/SECURITY.md`'s operator-responsibilities section gains its add-on
  paragraph here, not at the close.
- Unload correctness in wazero (instance lifetimes, module close semantics)
  is unproven in this codebase; the leak-bound test exists because "release
  the instance" is easy to write and hard to mean.
- A `required` add-on removed *while the instance depends on it for auth*
  (M65 class) changes sign-in behaviour at runtime; the act is the
  operator's and audited, and the consequence — external sign-in disappears,
  local continues — must be stated at the point of removal by whatever
  drives this API.

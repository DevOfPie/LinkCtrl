# M43 — Automation rules

**Depends on:** [M22](m22.md) [M35](m35.md) [M42](m42.md). **Discharges:**
completes the Other-surfaces row *QR codes, campaigns, webhooks, automation*.

## Done means

- `automation_rules` CRUD with a small documented trigger set: link expired,
  max-clicks reached ([M35](m35.md)), blocked attempt on the workspace
  ([M30](m30.md)).
- Action set: in-app notification ([M22](m22.md)), webhook event ([M42](m42.md)),
  and **archive link**.
- **No `disabled` action** (decision D10). `archived` and `disabled` produce the
  identical outcome on the redirect path — `snapshot.go` maps both to
  `OutcomeNotFound`, deliberately, so a scanner cannot tell them apart. `disabled`
  would therefore add a fourth status with no behavioural difference and **no
  restore affordance**, since restore targets archived: automation would create
  links in a state the UI offers no way out of. Plan.md's record that nothing sets
  `disabled` stands.
- Evaluation runs on the leader-elected scheduler, **never the request path**, with
  bounded per-run cost.
- `last_fired_at` is maintained. **A rule cannot trigger itself or loop**, tested —
  an automation that fires a webhook that fires an automation is the failure this
  names.
- Structure stays in the existing jsonb columns.
- Rule changes are audit events.

## Reopened 2026-08-04 — a cap that starves exactly the rules it says it does not

Reopened by the owner on [M44.9](m44.9.md)'s triage rather than succeeded, per
[workflow.md](../workflow.md)'s rule, so the correction carries this milestone's
number.

**What is false.** `internal/store/query/automation.sql:80-83` says the per-run
cap is *"ordered so the cap starves nobody: the rules a capped run skipped hold
the oldest watermarks on the next run and go first"*, and
`internal/domain/automation.go:211-214` says it again. Both are false, and
`internal/automation/automation.go:150-157` logs the cap with the same
reassurance.

`ListDueAutomationRules` orders `last_fired_at NULLS FIRST, id LIMIT $row_limit`
with `AutomationRulesPerRun = 100`. `last_fired_at` has two writers —
`ClaimAutomationRule` and a re-arm on disabled→enabled — and
`internal/automation/automation.go:217-223` returns **before** the claim whenever
`len(subjects) < config.Threshold()`. The default threshold is 1, so **every
zero-match run leaves the watermark exactly where it was**. There is no
`last_checked_at` column: `02900_automation.sql` and `00600_phase2_dormant.sql:109`
define one timestamp.

An idle rule therefore holds its place at the head of the queue permanently,
because idle is precisely what keeps a watermark old. The hundred oldest-watermark
enabled rules are a fixed set, and rule 101 is never evaluated on any run, ever.
A hundred rules is five workspaces at the documented per-workspace cap of twenty.
Nothing distinguishes such a rule from one whose trigger has not matched: it shows
as enabled, `last_fired_at` never moves, and no log line names it. Recorded as
[F83](../deferred-findings.md).

**What this reopening must not do.**

- **Do not advance `last_fired_at` on a no-match run.** It is the threshold
  accumulator, not a scheduler cursor — `automation.go:217-223` holds it
  deliberately so that sub-threshold matches accumulate across runs, and moving it
  discards subjects already inside the window. `min_count` stops working the day
  that changes.
- The ordering needs **its own column**, distinct from the watermark, so that
  "when was this rule last looked at" and "when did this rule last fire" stop being
  the same fact. Adding a column is additive DDL and is fine; the two must not be
  conflated again.
- Keep the per-run cost bounded — that is m43.md's own surviving bullet, and it is
  satisfied today. A fix that evaluates every rule on every run trades this
  finding for the one the cap exists to prevent.

## Risks

Trigger evaluation cost on the scheduler must be bounded. Keep the trigger
vocabulary small enough to test exhaustively — a large one is untestable and
becomes the place surprises live.

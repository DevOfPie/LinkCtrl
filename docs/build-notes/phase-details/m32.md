# M32 — Opt-in reputation and malware feeds

**Depends on:** [M30](m30.md) [M31](m31.md). **Discharges:** Security scope row
*Third-party reputation and malware feeds — opt-in, off by default*.

Reputation feeds mean sending someone's URLs to a third party, which is the
opposite of what this project promises. Everything below exists to keep that an
informed choice rather than a default.

## Done means

- With the feature off — the default — **zero destination URLs leave the
  instance**, asserted by test.
- Enabling requires explicit configuration naming the feed. Both the docs and a
  **read-only instance page** disclose plainly that destinations are sent to
  that third party (decision D40, 2026-08-01).

  The page **has no controls and accepts no POST**, asserted by test. That is
  the whole of what makes it safe to add one milestone after
  [D38](../../../Plan.md#phase-2-decisions-taken-after-the-plan-was-finalised)
  deleted the settings page: D38's finding was that this product has no
  instance-level principal, so nothing instance-wide may be *changed* from the
  dashboard. Reading is not changing. A control appearing here later would
  reverse D38 without anybody deciding to, so the test is the mechanism and not
  the convention.

  It states which third party, what is sent, when it is sent, and that only the
  operator can change it.
- Feed verdicts act only as **low-confidence signals**: disputable,
  owner-overridable, never promoted to the embedded tier. A test proves every
  built-in tier behaves identically with feeds on, off, or erroring — the feeds
  are never the mechanism the built-in tiers depend on.
- Feed failures fail open to the built-in tiers, with a counted metric.
- Plan.md's no-destination-leaves-the-box promise is updated to state the opt-in
  exception precisely, rather than being quietly falsified.
- Ships with a single generic HTTP feed adapter. Which feeds get first-class
  support is a later product call, not a blocker.
- **Addendum (decision D1):** with the mailer configured, dispute outcomes are
  also emailed. In-app delivery remains the baseline.

## Reopened 2026-08-04 — the promise this milestone was told to keep precise

Reopened by the owner on [M44.9](m44.9.md)'s triage rather than succeeded, per
[workflow.md](../workflow.md)'s rule, so the correction carries this milestone's
number.

**What is false.** This milestone's own bullet says *"Plan.md's
no-destination-leaves-the-box promise is updated to state the opt-in exception
precisely, rather than being quietly falsified."* It was updated for the feed, and
then quietly falsified by [M42](m42.md). Four sites now over-promise:

- `Plan.md:215-217` — *"no destination is sent anywhere unless the operator sets
  `LINKCTRL_FEED_URL`, and the shipped default is unset"*
- `docs/SECURITY.md:207-208` — the same, called *"the whole of the promise"*
- `docs/SECURITY.md:215-216` — *"The feed is asked **last**, so a destination any
  built-in tier refuses is never sent anywhere"*
- `README.md:151` — *"One thing can leave the box, and only if you turn it on"*

`internal/link/webhook.go:379-386` puts `"url": l.URL` — the raw destination — in
all five link-lifecycle payloads, and `:403-409` puts `"url_defanged"` on
`destination.blocked`, which is exactly the tier refusal `SECURITY.md:215-216` says
is never sent anywhere. `internal/config/config.go:952-955` states plainly that
there is no operator gate: *"there is no switch: webhooks are a workspace feature
rather than an operator one."* So the egress needs `webhooks.write` and no operator
act at all. Recorded as [F86](../deferred-findings.md).

`README.md:151` is contradicted by `README.md:87` on the same page.

**What this reopening must not do.**

- **This is documentary. Do not "fix" it by changing the payload.**
  `internal/link/webhook.go:366-372` declares that map a published interface and
  `docs/usage.md:1253` documents both fields; receivers parse them. Removing `url`
  would break every integration to make a sentence true.
- **All four sites, plus the `url_defanged` leg.** Amending Plan.md and README
  while leaving `SECURITY.md:215-216` is the likely half-fix, and that line is the
  strongest of the four — it is the one that names the refused-destination case
  specifically.
- The replacement wording has to be **precise rather than vague**. "Data may leave
  if you configure it to" is not what this milestone was asked for; the honest
  statement names the two channels, says which one is the operator's and which is a
  workspace member's, and says what each carries.
- Nothing here is a security regression to fix: the capability is disclosed at
  `docs/SECURITY.md:60` and `docs/usage.md:1253`. What is wrong is four summary
  claims that contradict it.

**Widened at step 3.4, 2026-08-04.** The first worker found that F86 undercounted:
there are seven sites, not four, and reported them rather than fixing them —
correctly, since the loop rejects work no bullet asked for. Two of the three are
**in spec here** under [phase-loop.md](../phase-loop.md#1-validate)'s deferred-overlap
rule, because they are this milestone's own claim in other words and leaving them
would land a `done` row asserting something untrue:

- `CHANGELOG.md:750` — *"a destination your own rules refuse is never sent
  anywhere"*, word for word the claim this section calls the strongest of the four,
  **inside M32's own `[Unreleased]` entry**. A false sentence in the changelog for
  the feature being corrected is the one place it cannot stay.
- `test/integration/feed_test.go:360-366` — the comment and failure message say
  *"must never leave the box"* where the assertion covers the feed alone. The test
  is right; its words are not. Correct the words, do not touch the assertion.

The third stays open as [F134](../deferred-findings.md) and is **not** in spec:
`docs/SECURITY.md:73` says *"**Two** outbound connections are possible and both are
off until an operator configures them"*, and fixing it means re-deriving the count
rather than editing a sentence — whether the domain-verification job's hourly DNS
to a registrant-chosen nameserver is a third or fourth outbound connection is a
judgement, and judgements are the owner's.

## Risks

The disclosure wording is the deliverable as much as the code is. An operator who
enables this without understanding it has been failed by the UI, not by the
feature.

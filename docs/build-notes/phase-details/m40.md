# M40 — Custom domains: verification and serving

**Depends on:** [M39](m39.md) [M23](m23.md). **Discharges:** Other-surfaces scope
row *Custom domains, per workspace and per link*; the domain-filter promise in
`internal/store/query/links.sql`.

The security-heaviest milestone of the phase. The gap between "registered" and
"verified" is an alias-namespace hijack, which is why it is a milestone boundary
rather than a code branch.

## Done means

### Verification

- A DNS TXT challenge — token per domain, additive columns — checked by a
  leader-elected job and on demand.
- **Only after `verified_at` is set** does the host router resolve aliases on that
  hostname. An unverified or unknown host stays ops-only 404, and a wrong-host
  request is never a cross-host redirect. Both tested.
- Re-verification runs on a cadence. The **deleted-CNAME plan** is implemented and
  documented: serving stops or degrades per the recorded decision, never silently
  persists.

### Serving

- **TLS is operator-managed via Caddy on-demand TLS** (decision D3), with a
  documented config block including an ask endpoint that answers only for verified
  domains. The app tracks `ssl_status` only and never speaks ACME itself — built-in
  ACME would contradict the no-third-party-calls posture.
- Link creation can target an owned verified domain; `short_url` builds from it.
- Alias uniqueness stays `(domain_id, alias)`; reserved aliases apply on every host.
- Hostname-to-domain resolution on the redirect path is cached **with invalidation
  wired into [M23](m23.md)'s pub/sub** — no per-request query, and no replica
  serving a domain that was just unverified. This is the cross-replica staleness
  gap the plan review found in both rival orderings.
- `GetDefaultDomainSettings` gains the domain filter its own comment promises, and
  the links list gains a domain filter.
- Per-domain root redirect works via the existing `root_redirect_url` column and is
  an audit event.
- SLO re-verified: cached p99 under 20ms.
- Deployment docs gain the custom-domain runbook.

## Reopened 2026-08-04 — the gate can be made to verify a name nobody proved

M40 shipped and the claim its whole security story rests on turned out false.
Reopened by the owner on [M44.9](m44.9.md)'s triage rather than succeeded, per
[workflow.md](../workflow.md)'s rule, so the correction carries this milestone's
number. Two rows, one file, one reopening.

**What is false, first.** The bullet above says serving begins **only after
`verified_at` is set**, and `domains.sql:71-76` argues that a rename un-verifies
*"so carrying `verified_at` across would let a workspace verify a name it controls
and then rename the row to one it does not"*. That is exactly what can happen.
`internal/link/verification.go:166` reads the row, `:175` resolves DNS against the
hostname it read — up to `DOMAIN_VERIFY_DNS_TIMEOUT`, and against a nameserver the
registrant controls — and `:201` writes `MarkDomainVerified(ctx, row.ID)`, whose
statement is `WHERE id = $1 AND deleted_at IS NULL`. Nothing re-reads the hostname,
nothing compares the token again, there is no transaction and no `FOR UPDATE`. A
concurrent `PATCH /api/v1/domains/{domainID}` renaming the row lands in the gap,
and `COALESCE(verified_at, now())` then fills the NULL the rename just wrote.

**The impact is not what the row was filed as.** Nothing in the tree refuses the
instance's own names — D69 declined to check registrations against them, reasoning
that no router matched a Host header against the table, which M40 changed — and
`customHostRouter` sits in front of both router branches. So the name renamed into
can be the instance's **app host**, which puts the dashboard and the API behind the
custom mux, or its **link host**, which repoints every alias lookup at the
attacker's `domain_id`. DNS and certificates for both already exist. Recorded as
[F76](../deferred-findings.md).

**And the audit trail does not catch it**, which is the part worth fixing
deliberately: `MarkDomainVerified` returns the row, and `verification.go:206-208`
consumes that return only to stamp the audit record with `verified.Hostname` — so
the log records the *new* name as having been verified.

**What is false, second.** The same bullet promises re-verification *"runs on a
cadence"* and that the deleted-CNAME plan is implemented. `RegisterDomain` caps
nothing — there is no per-workspace domain count anywhere, unlike campaigns and
folders — and `ReverifyDomains` walks one batch serially, ordered
`verification_checked_at NULLS FIRST`, each row blocking up to five seconds inside
a ten-minute job budget. Rows the loop reaches do get a watermark, but
`RenameDomain` resets that column to NULL, so one `PATCH` per row returns it to the
head of the queue indefinitely. Verified tenants carry non-NULL watermarks and sort
last, so `UnverifyDomain` never fires for them and the hard stop D70 and D71 argue
for silently stops running instance-wide. Recorded as
[F84](../deferred-findings.md).

**What this reopening must not do.**

- **Do not wrap the read and the write in one transaction and call it fixed.** The
  rename commits in the gap between two separate transactions, so a transaction
  around the verify path does not serialise against it. Holding `FOR UPDATE` across
  the DNS lookup is worse: it pins a row lock for the lookup timeout, inside a job
  that walks up to `DOMAIN_VERIFY_BATCH` rows.
- The shape that closes it is a **conditional write** — the update predicated on the
  hostname and token that were actually checked, with an explicit zero-rows-affected
  branch — and it must be applied at **both** sites: `verification.go:201` and the
  job's own write at `:314`, which has the identical shape.
- **Do not fix F84 by raising `DOMAIN_VERIFY_BATCH`.** More rows inside the same
  ten minutes is strictly worse. Adding concurrency to the lookups without also
  bounding domains per workspace turns the leader into an outbound DNS amplifier
  any tenant can aim.
- A per-workspace cap must not break the case `verification.go:339-343` protects —
  a hostname registered before its DNS cut-over, which fails every check until its
  owner publishes — and nothing may treat a NULL `verification_checked_at` as
  evidence of abandonment, because `RenameDomain` writes that NULL on a live row.

## Risks

Any gap between registered and verified is an alias-namespace hijack: a stranger
registers your hostname and serves links on it. The verification gate is the whole
security story of this milestone.

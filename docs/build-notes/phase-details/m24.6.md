# M24.6 — Dark mode, actually applied

**Depends on:** [M24.5](m24.5.md). This corrects its stylesheet and moves the
control it added, so it cannot land before it.
**Discharges:** [deferred-findings.md](../deferred-findings.md) F3 (dark mode has
no effect on the UI) and F4 (the control is in the footer). Owner-scheduled,
2026-07-31.

M24.5 shipped a theme that no browser applies. Its light tokens are declared in
an unlayered `:root` and its dark tokens inside `@layer base`, and unlayered
declarations beat layered ones whatever their specificity — so both dark paths,
the explicit override and `prefers-color-scheme`, lose to the light values every
time. The server half is correct and stays as it is: the attribute renders, the
cookie works, and nothing about the no-flash design is implicated.

This milestone makes M24.5's claims true, and moves the control from the footer
to where somebody would look for it.

## Done means

- The dark token values apply. Light and dark token blocks sit in the **same
  cascade context**, so `:root[data-theme="dark"]` wins on specificity and
  source order rather than losing to an unlayered rule.
- `TestThemeTokensShareOneCascadeLayer` (new, `internal/ui`) parses the built
  `app.css`, finds every top-level construct declaring a `--t-*` token, and
  fails when they do not all share one layer context. It fails against the
  stylesheet as M24.5 shipped it — demonstrated by running it before the fix,
  not asserted. This is the enforcement M24.5 lacked:
  `TestTemplatesUseThemeTokensOnly` checks that templates *name* tokens and
  nothing checked that a token's *value* ever changes.
- Every `--t-*` token defined in the light block has a counterpart in each dark
  block, asserted by that same test. A token added to one and forgotten in the
  other is the next version of this defect.
- The **Appearance** control lives on the account page
  (`internal/ui/templates/pages/account.html`) — System, Light, Dark, still a
  plain form POST with no JavaScript.
- The sign-in page keeps its own control. M24.5's per-browser design is only
  meaningful if the preference is settable before there is an account, and
  account settings need a session. One shared partial, rendered in two places.
- The footer control is removed, so exactly one control renders per page —
  asserted by template test across the eight pages, signed-in and signed-out.
- `TestEveryPageRenders` still passes at all three cookie states, and the
  attribute assertions M24.5 added are unchanged and still green. The server
  side is not being rewritten.
- Verified live against the composed stack, not only by test: a dashboard page
  and the sign-in page are each fetched dark, light and with no cookie, and the
  **rendered token values differ** between them. The M24.5 check confirmed only
  that the attribute was present, which is exactly how this shipped broken.
- M24.5's contrast figures are unchanged and not re-measured. They were computed
  correctly against token values this milestone does not alter; they were simply
  describing values no browser reached. Their claim becomes true by this fix,
  and a bullet claiming fresh measurement would be false.

Deliberately unchanged: the cookie (`linkctrl_theme`, HttpOnly, unprefixed, one
year), the no-JavaScript stance, the server-rendered attribute, and the decision
against a `users` column. Deliberately still unthemed: `/docs`, transactional
mail ([M26](m26.md)), and [M41](m41.md)'s QR codes.

## Risks

The cascade fix is small and global. Moving the token blocks changes which rules
win across every page at once, and getting it wrong inverts the themes rather
than failing loudly — which is why the test asserts the layer relationship
directly instead of trusting that dark "looks right" in one screenshot.

The control move touches `layout.html`, which every page renders, and adds a
render site on a page reachable without a session. The sign-out path is the one
to watch: a control that assumes account context will panic or render empty on
the sign-in page, and that page is the whole reason the second render site
exists.

# M46.6 — The workspace pair reads as one control

**Depends on:** [M46](m46.md), which built both halves of the pair, and
[M46.5](m46.5.md), **hard** — the chevron-only face and the 360px bound are
rendered-appearance claims a template test cannot see, and M46.5 is what makes
a browser assertion keepable. The work touches `partials/nav.html`'s
`workspace_label` and `workspace_switch`, **their invocation site** — the two
are siblings inside `layout.html`'s `<div class="ml-auto …">` (`layout.html:60-62`
at `ddd5798`), so the shared container is a wrapper there or a boundary built
across the two defines, and the milestone records which — and the tests that
hold them. [M47](m47.md)'s scope is the link page; the plan expects no file
overlap, and validation re-checks that rather than this line guaranteeing it.
**Discharges:** [F204](../deferred-findings.md#open). **Owner-added scope,
2026-08-11**, approved into Phase 3 on the owner's ground that this phase has
carried the UI and UX changes and the fix belongs with them.

The shape was **chosen from wireframes, not from prose** — four shapes drawn in
the product's own tokens, both membership states each, and the owner picked B1
then amended it: the switch affordance is the **chevron alone**. The wireframe
artifact is the picture; this file is the contract. If they disagree, this file
wins.

Numbered `.6` because the fix depends on M46 alone and sits beside it, below
[M57.9](m57.9.md) per [W43](../workflow-changes.md#made) — the review reopens
with it, as it already has for three insertions — and `.7`/`.8` stay free.

## Done means

### One boundary, two elements, nothing restructured

- `workspace_label` and `workspace_switch` render inside **one bordered
  container** that reads as a single control: label, a hairline divider, then
  the select. Structurally the pair survives — still the label `<p>` and the
  form-wrapped `<select>`, side by side — because shape (b)'s whole argument
  was *changes nothing structural*, and the three recorded owner answers it
  preserves are the point:
  - the current workspace is **never an option** in the switcher (blind task 9,
    M46's comment at `nav.html:41-56` at `ddd5798`);
  - the switcher still renders **only above one membership** (M25 — no control
    that can do nothing);
  - the label still names the workspace **whenever one is current**.
- **The select's closed face is the chevron alone.** Owner-amended from B1 as
  drawn: no "Switch" text, no placeholder text visible when closed. Its
  accessible name stays *Switch workspace* — `aria-label` already carries it —
  and the opened list keeps its order — disabled placeholder first, then every
  workspace that is not current — with the placeholder's **label empty**,
  because the chevron-only face forbids it text: a three-engine probe showed
  `color: transparent` erases the native arrow in Chromium and Firefox, so the
  empty-labelled placeholder is the only cross-engine mechanism. *(Amended at
  acceptance, 2026-08-11 — this bullet first said "the opened list is
  unchanged", which the mechanism this file's own Risks section sanctions
  cannot satisfy; see decisions.md.)* A sighted reader gets the affordance
  from the boundary and the arrow; a screen reader loses nothing.
- **At one membership the container renders with the label alone** — no
  divider, no select, no dead affordance. The account stays named in the same
  box, so the shell reads identically whether or not there is anywhere to go.
- **At zero memberships the container does not render at all.** An account
  belonging to nothing has no workspace to name (D36) — the label already
  emits nothing and the switcher already emits nothing, and the container must
  not survive them as an empty bordered box. Three states, all specified:
  none, one, several.
- **Focus stays visible inside the shared boundary.** The select remains the
  only focusable element of the pair — the label is a `<p>` — and a keyboard
  user tabbing to it must see focus indicated within the fused control, not
  suppressed by the shared border. The existing `focus:border-accent` idiom
  applied to the container or the segment is the expected mechanism; whichever
  is chosen is visible in every engine at the `X.9` check.

### Asserted by test, in all three membership states

- A `internal/ui` test renders the nav at **zero**, **one** and **two**
  memberships and asserts: the shared container present at one and two and
  **absent at zero** — including the divider, present only at two; the select
  present only at two; the current workspace never among the options; the
  label text present at one and two. The existing assertions this design
  preserves — `workspace_test.go:60-64` (never offers current), `:68-71`
  (disabled placeholder), `:135` (label present when a workspace is current)
  and `:150-156` (label **absent** on `organization_new`), cited at `ddd5798`
  — encode recorded owner answers (blind task 9, M25, D36). **Changing any of
  them is a prompt**, because it reverses a recorded answer; any other test
  adjustment is called out and justified in the commit.
- **A kept browser assertion, in M46.5's idiom**, asserts what the template
  test cannot: the select's closed face shows **no visible text** — the
  chevron alone — and the header does **not overflow a 360px viewport**,
  which is where the 360px bound below is measured. Extends or sits beside
  `tools/agent-browser`'s kept spec; sabotage-verified like everything else.
- A test that passes first try is sabotage-verified: break the thing it
  protects, confirm red, restore by counter-edit. Never `git checkout`.

### Behaviour does not change

- Switching still posts `workspace_id` on change through htmx to
  `/workspace/switch` with the hidden `next`; the handler is untouched. This
  is a restyle of two template definitions, not a mechanics change.
- Truncation survives restyling: `min-w-0` and `truncate` on both label
  halves, the pair repeated in `title`, and the fused control must not push
  the header past 360px — the constraint that shaped the label in the first
  place (`nav.html:27-29` at `ddd5798`), measured by the kept browser
  assertion above.
- Both themes via the theme tokens; [M24.5](m24.5.md)'s template scan applies
  unchanged — **and its limit is stated rather than leaned on**: the scan
  matches raw palette utilities and cannot see a hex colour inside a
  `background-image` data URI, which is the standard way to draw a chevron on
  an `appearance-none` select. So the chevron's colour comes from
  `currentColor` or a theme token, never a literal hex the scan is blind to;
  and the CSP is `style-src 'self'` with no waivers, so nothing here arrives
  as an inline `style=` attribute — whatever clips the closed face's text
  lives in `app.css`.

### Demo

- **Nothing new to seed.** The demo already shows the pair wherever it shows
  the shell; the restyle is visible on every page. `demoCoverage()` gains no
  row. Stated so the omission reads as considered.

- **No switcher at one membership** — shape (c) was drawn and declined; M25

## Risks

**Low, and concentrated in the one thing the design bets on**: that a shared
boundary makes the pair read as one claim — *this is where you are; here is
how you leave*. The chevron-only face is the owner's amendment and spends the
least width of any drawn shape, but a chevron with no text is also the most
implicit affordance in the shell; if the bet is wrong, the blind tasks at
[M57.9](m57.9.md)'s re-run are where it shows, and the fallback drawn and
recorded is B1's "Switch ▼" face.

A `<select>` whose closed face must show only a chevron needs styling care —
a native select renders its selected option's text. The likely mechanism is a
fixed-width select with the placeholder's text clipped or transparent, or an
explicit empty-labelled placeholder; whichever is chosen must keep the opened
list readable in every engine. The kept browser assertion is the gate that
sees the closed face; the `X.9` review's three-engine check is what sees the
opened list.

# Reopened — 2026-08-11

**The milestone above shipped and one of its claims did not survive the
owner's first look.** [F209](../deferred-findings.md#open) records four
symptoms named on sight, all one cause: the opened state is a native
`<select>` popup, which cannot be positioned, styled, or purged of its blank
placeholder row — and the closed face paints the selected option's text until
the redirect lands, which transiently falsifies the shipped claim that *the
closed face is the chevron alone*. Work below carries M46.6's number, because
a reopening keeps its milestone's number.

**Reviewed by [M57.9](m57.9.md)**, whose reopened range already contains
M46.6 ([W44](../workflow-changes.md#made)). Dependencies unchanged: M46,
M46.5 hard.

## Done means, as reopened

### The opened state is the shell's own menu, not the engine's

- The switcher's opened state is rebuilt on the **Popover API pattern both
  header menus already use** (D24): the chevron becomes a
  `<button popovertarget>` invoker inside the fused control, and the panel is
  a `popover="auto"` element styled in-product — same tokens, same border and
  radius idiom as the control it hangs from, so it reads as the control
  opening rather than a bolted-on afterthought.
- **The panel is right-aligned with the fused control.** A top-layer element
  positions against the viewport, not the header — the recorded idiom in
  `nav.html`'s menu comment is the mechanism, and the alignment is looked at
  in a browser rather than inferred, then asserted by the kept spec.
- **No placeholder row exists to draw.** The panel lists exactly the
  workspaces that are not current, each one a **submit button** in the
  existing form (`workspace_id` on the button's value, hidden `next`
  untouched), so selecting is still one POST to `/workspace/switch` and the
  handler is untouched.
- **Nothing can flash.** The invoker is a button whose face is the chevron
  glyph; it has no selected-option text to paint, before, during, or after a
  switch.
- Escape and outside-click dismiss, and only one auto popover opens at a
  time — behaviour the pattern carries by construction, stated because it is
  what D24 bought.

### What survives, and the one assertion that retires

- Every recorded answer the pair encodes still holds and stays asserted: the
  current workspace is **never** in the list (blind task 9); the switcher
  renders **only above one membership** (M25); the label names the workspace
  whenever one is current, and the container keeps its three states (D36).
- `workspace_test.go`'s **disabled-placeholder assertion retires with its
  premise**: a select must display something, a button need not. Approved by
  the owner in approving this reopening — F209's row names the cost. The
  test's replacement asserts the panel holds no blank entry and no
  current-workspace entry.
- A11y shifts from combobox to button-and-group, **the same recorded trade
  (D24) the other two menus made**; the invoker keeps the *Switch workspace*
  accessible name, and every option is a real button naming its workspace.

### Asserted where the defect lived

- The kept browser spec extends to the opened state, which is where all four
  symptoms lived and where no template test can see: panel right edge aligns
  with the control's right edge; the panel holds no blank row; the invoker's
  face carries no text after a switch is triggered; 360px still holds.
  Sabotage-verified, as everything else.

## Deliberately not done, as reopened

- No change to the switch handler, the form semantics, or `next`.
- No `role="menu"` — the honest trade D24 recorded stands.
- No change to the closed face's design: the fused control, divider and
  chevron-only face are the shipped, owner-confirmed design and stay.

## Risks, as reopened

**The popover idiom's positioning is viewport-anchored by two literals**, and
the switcher sits mid-bar rather than at the bar's edge like both existing
menus — right-aligning a viewport-anchored panel to a mid-bar control is the
one place this pattern has not been exercised. If the literals cannot express
it, anchor positioning or a measured inset is the fallback, and whichever is
used is recorded. The kept spec's alignment assertion is what keeps this
honest across the three engines.

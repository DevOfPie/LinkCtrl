# M22 — Notifications: in-app behavior

**Depends on:** nothing. **Discharges:** the *notification* leg of the Security
blocking row (Plan.md states dispute review and outcome notices fit the dormant
`notifications` table as it stands).

## Done means

- A notification service writes rows to the existing `notifications` table with
  **zero DDL** — structure goes in the `data` jsonb, per the dormant-table rule.
- `GET /api/v1/notifications` and a mark-read operation exist.
- The nav shows an unread count backed by the existing partial unread index; a
  notifications page renders, with a `pageData` entry and render tests.
- The reserved alias `notifications` already covers the route;
  `TestReservedListCoversRegisteredRoutes` passes unchanged.
- Named consumers wired or ready: audit-log growth threshold ([M21](m21.md),
  decision D5), dispute filed and dispute resolved ([M31](m31.md)), invite
  accepted ([M27](m27.md)), automation notify action ([M43](m43.md)).

## Fence

Scope is the delivery substrate its named consumers need — **no push, no
per-event preference machinery, no general notification centre**. No scope row
asks for one, and the judges flagged over-building here as this milestone's main
risk. Email is [M26](m26.md)'s concern, not this table's.

## Risks

Low. The only real one is scope drift into a preferences system.

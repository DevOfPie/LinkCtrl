# M50.8 — The QR tab's third report, and the first script the dashboard depends on

**Depends on:** [M50.7](m50.7.md) *(hard — eight of the ten limbs edit controls
M50.7 built, and building against the pre-M50.7 row would lay out a surface that
no longer exists)*, [M50](m50.md) *(hard, for the list's sort and the last code's
remove button)*, [M50.6](m50.6.md) *(hard — the logo section this milestone
folds away is the one its second reopening rewrote)*.
**Discharges:** [F238](../deferred-findings.md#open), owner-approved as work
2026-08-14. Owner-added scope the same day, from the third QR-tab report.

The tab has now been reported three times. The first two produced reopenings and
[M50.7](m50.7.md); this is the third, and what makes it a milestone rather than
four reopenings is the same argument M50.7's file makes — most of these items
are not defects. Three of them **reverse a choice this repository argued for in
writing**, which is stated per bullet rather than left for a reader to notice.

**This milestone exhausts the M50 band.** `M50.9` is reserved for reviews
([planning.md §4](../planning.md#4-numbering)), so nothing can be inserted
between M50 and M51 after this. An eleventh item on this tab is a reopening or a
Phase 4 row, and that is now a fact about the numbering rather than a preference.

## Done means

### The list stops moving under the reader

- **Codes are listed alphabetically by name, case-insensitively**, and the
  order does not change when the default moves. Owner-set:
  *"Selecting a different default code re-orders the list of codes which can
  make it seem like the selection didn't change."*
- **This reverses `ListQRCodes`' stated design.** `internal/store/query/campaigns.sql:167`
  is `ORDER BY (NOT (q.is_default OR q.slug = '')), q.created_at, q.id`, and the
  comment above it defends the re-order in as many words — *"the list re-orders
  when the reader moves it, which is the visible half of what setting a default
  does"*. That argument is not withdrawn; it is answered. The filled icon
  M50.7 put on every row is what makes the change visible now, so the sort no
  longer has to carry that job, and carrying it was what made the change look
  like nothing happened.
  *Enforced by:* an **integration** test asserting the returned order for a set
  whose alphabetical and creation orders differ, **and** that moving the default
  does not change it. The sort is `lower(q.label)` with a stable tie-break, so
  it matches `ORDER BY lower(c.name), c.id` at `:49` rather than inventing a
  second collation for the same product.
  *(Amended at step 3.4: this read "an `internal/link` test". The order is SQL —
  a unit test there would have to fake `dbgen.Querier` whole and would assert
  the fake. The test drives `link.Service.ListQRCodes`, the surface this bullet
  names, against Postgres. D193 argues it.)*
- **The default is still identifiable without reading**, which is what the
  sort used to buy: the filled icon (`partials/link_qr.html:257`) and the meta
  line's *"the default"* both stay.
- **Three records cite the old order and are part of this milestone, not
  cleanup.** `internal/store/query/campaigns.sql:169-176` justifies promoting
  the oldest code by *"the promoted code is the one at the top of the list the
  reader is looking at"* — which alphabetical breaks —
  `internal/link/qr.go:247` says the service *"returns every code a link
  carries, default first"*, and `internal/httpx/web_links.go:675` says the same
  of the view field it fills from that service: *"The link's codes (M50),
  default first"*. **The promotion rule itself does not change**: D183
  set it to the oldest and nothing here reverses that; what changes is the
  sentence explaining why it looks natural, which stops being true. All three
  are corrected in this milestone's diff. *(The first two were found by the plan
  review as a hidden edge; the third by the milestone's reviewer, and the count
  was amended at step 3.4 — see decisions.md.)*

### The size control tells the truth while it moves

- **The slider and the number follow each other, live, in both directions.**
  Owner-set: *"Dragging the Size slider doesn't change the number next to it
  until you save. The number should change with the slider as well as the
  reverse."*
- **This is the first script this product's dashboard depends on**, owner-decided
  2026-08-14 over dropping one of the two inputs. *(Not the first script it
  writes: `internal/ui/static/js/docs.js` is 34 hand-written lines booting
  Swagger UI on `/docs`, written because the CSP forbids inline script. The plan
  review caught the overclaim. The edge that is real, and the one the precedent
  argument rests on, is that no script has ever driven a **control on the
  dashboard** — docs.js boots a vendored viewer on a page of its own.)*
- **It reverses a written argument**, which this milestone names wherever it
  does one: `partials/link_qr.html:485-489` says *"Nothing in this browser can
  copy a dragged slider into the box beside it: this dashboard runs htmx and no
  script of its own, and a `script-src 'self'` page is not the place to
  introduce one for a form control."* That is the sentence the owner overruled.
  What it defends — the arbitration between `size_shown` and the requested
  size — **must survive as the script-blocked path**, which is the degradation
  bullet below.
- **What it does not cost.** A served file under `script-src 'self'`: the CSP is
  **unchanged**, no `unsafe-` waiver, no Node, no CDN, no build step, which is
  the whole of what the inherited *`ui` stays stdlib-only* rule asks.
  `htmx.min.js` and `docs.js` are already served from the same directory.
  *Enforced by:* a case in the kept browser suite dragging the slider and
  reading the number, and typing in the number and reading the slider. **A unit
  test cannot see this** — it is the one claim in this milestone that only a
  browser can make, and it is why the suite is the enforcement rather than a
  template assertion.
- **It degrades to today's behaviour with the script blocked.** The number
  input keeps its own value and the form still submits it, so a reader with
  JavaScript off loses the live echo and nothing else.
  *Enforced by:* a template test asserting both inputs still carry `name=` and
  their values, and a browser case with scripts disabled asserting the form
  still saves.

### A save returns you to where you were

- **A style write lands back at the QR tab's scroll position**, not at the top
  of the page. Owner-set: *"The whole page resets to the top every time the
  save button is used… a force to top is jarring and bad UX."*
- Every write redirects through `qrReturn` (`internal/httpx/web_qr.go:103`) and
  none of them carries a fragment, so the browser lands at the document top.
  **The milestone does not specify the mechanism** — a fragment on the redirect
  and a scroll restoration in the script are both available, and which is right
  depends on whether the tab's position or the control's is what a reader
  expects to return to. The build chooses, argues it in a decision entry, and
  says what it rejected.
  *Enforced by:* a browser case scrolling down the tab, saving, and asserting
  the reader is still where they were.
  *(Amended at step 3.4: this read "scrolling to the size control … asserting
  the control is still in the viewport". The case scrolls to and asserts the
  **Save** button, which is the control a reader is actually on when a write
  happens and is what makes the assertion distinguish a restored position from
  the `#qr` fragment's own landing. The claim — a save returns you to where you
  were — is unchanged and is what the case tests.)*

## Risks

**The script is a precedent before it is a feature.** Ten lines binding two
inputs is easy; what is not easy is that every later control can now cite it.
The milestone's answer is the *deliberately not done* list above and a decision
entry that says what the file is allowed to contain, so the next request argues
against a written bound rather than against nobody.

**A browser-only claim is a claim the unit suite cannot defend.** The live
slider, the scroll restoration and the hover feedback are all only checkable in
a browser, so this milestone leans on `make verify-ui` more than any before it.
A spec that silently stops running looks exactly like a spec that passes —
[F237](../deferred-findings.md#open) is the same shape one level down — so each
new case asserts its own precondition rather than only its conclusion.

**Reversing two written arguments invites reversing them back.** The sort and
the disabled-remove-button both had reasons, and both reasons survive their
reversal — the sort's job moved to the icon, the comment's objection is
answered by the tooltip. Recording *why the old argument no longer applies* is
what stops the third report on this tab from being undone by the fourth.

**The prose bound is being moved by the milestone that has to meet it.** M50.7
set 900 and this sets a lower one from its own measurement, which is the shape
of a gate marking its own homework. The rounding rule above is the guard: the
number comes from a measurement rounded up to the next fifty, not from whatever
the build happened to land on.

### The save returns you to where you were, without showing you somewhere else first

- **F244(a), and it is a defect in this milestone's own new code.** Owner:
  *"immediately upon changing the default the screen reloads at the top of the
  page then jumps down to match the previous scroll position."* The reader does
  arrive where they were. They are shown the top of the card on the way, and
  *"a save returns you to where you were"* is not what a jump-and-settle looks
  like.
- **The mechanism is written into the code that causes it.**
  `internal/ui/static/js/qr-size.js:179-199` says the restore is applied a
  second time *because* the browser performs its `#qr` fragment scroll after
  `DOMContentLoaded` — so the correcting scroll is necessarily after a paint.
  The fragment is put there by `internal/httpx/web_qr.go:131`,
  `return page + "?" + q.Encode() + "#qr"`, and it has been on that redirect
  since D178, long before a script existed to fight it.
- **D193 chose the remembered position over the fragment and left the fragment
  in place.** That is the thing to correct: two mechanisms are aiming at the
  same scroll and the second one exists to undo the first. **The milestone does
  not specify which goes** — removing `#qr` from the link-page redirect, or
  restoring before first paint, are both available and they cost different
  things. `#qr` is also what `restore()` tests for to decide the tab rendered at
  all, and D178 records the fragment as part of the return path, so removing it
  is not a one-line deletion. The build chooses, argues it in a decision entry,
  and says what it rejected.
  *Enforced by:* a browser case asserting the position is **never** somewhere
  else between the load and the settle — not merely that it settles correctly,
  which is the assertion that already passes and did not catch this.
- **The harness could not see this and that is part of the finding.** Two probes
  missed it: one searched for `button[name="default"]` where the control is
  `name="make_default"` and skipped in silence, and one let the driver
  auto-scroll the control into view so the stored position was never the
  reader's. A case that cannot fail is [F237](../deferred-findings.md#open)'s
  shape, and this milestone's own risk section named it. **Every case added
  here asserts its own precondition**, including that the control it drives
  exists.

### The position is applied before the first paint

- **F246(a), and it is the option this milestone named at its first reopening
  and did not take.** Removing `#qr` was the other, and it was right as far as it
  went: the fragment is gone and no second mechanism is aiming at the scroll.
  What is left is that **nothing has been restored yet when the browser first
  paints**. `templates/layout.html:31` loads the script `defer`, so
  `static/js/qr-size.js:235-239` takes its `else` branch — readiness is already
  `interactive` when a deferred script runs — and `restore()` therefore fires
  after the parse and after the render-blocking stylesheet, which is after the
  document has been painted at the top. The correction the owner sees is now
  *top → position* instead of *`#qr` → position*; it is the same correction.
- **The variable is round-trip time, which is why four probes and one kept case
  have all said this page is fine.** Measured 2026-08-15 at `928504f`: chromium
  1280×800 against the test instance, `scrollY` traced from `addInitScript` —
  before the document's own scripts — through every `scroll`,
  `readystatechange`, `DOMContentLoaded`, `load` and animation frame, over 3–8
  rounds per profile of Save, the default flag and a code selection. Frames
  painted at the wrong position per Save, the default flag matching within one
  frame:

  | profile | frames | visible for |
  | --- | --- | --- |
  | localhost, unthrottled | 0 | — |
  | 20 ms · 20 Mbps · 1× CPU | 2 | ~85 ms |
  | 40 ms · 8 Mbps · 2× CPU | 4 | ~151 ms |
  | 80 ms · 4 Mbps · 2× CPU | 8–9 | ~300 ms |
  | 150 ms · 1.5 Mbps · 4× CPU | 19–22 | ~650 ms |

  Every round of every throttled profile flashed; no unthrottled round did. The
  owner reaches the demo over the public internet, and the demo serves this
  script byte-identically from an image built 29 seconds after `928504f`.
- **The milestone does not specify the mechanism, and one obvious one is
  already closed.** `script-src 'self'` carries no `unsafe-inline` and no nonce,
  so the restore cannot become an inline script in `<head>`. A parser-blocking
  `<script src>` ahead of the body, a body held back until the position is
  applied, and moving the offset off `sessionStorage` onto something the server
  can render are all available and cost different things — a render-blocking
  request on every page of the dashboard, a paint the reader waits for, and a
  scroll position that leaves the browser. The build chooses, argues it in a
  decision entry, and says what it rejected. Whatever it picks, **the reader is
  never shown a position they did not stand at** — no painted frame of the
  loaded document carries the wrong offset.
  *(Amended at acceptance, 2026-08-16, fact-level. It read **the position is
  applied before the first paint of the loaded document**, not corrected after
  it — which names the shape of one of the three mechanisms this same bullet
  offers rather than the requirement they share, and the build took a different
  one of the three. D196 establishes that the literal reading describes nothing
  buildable: a script running before the first paint runs before the document
  has a height, and `scrollTo` against it clamps to 0. The assertion is
  unchanged, which is why this is an amendment and not a prompt — a held paint
  and a beaten paint both satisfy it, and the menu above already priced the
  hold.)*
  *Enforced by:* the browser case that already asserts this claim, run under
  **emulated network conditions** instead of against localhost.
  `specs/qr-tab-controls.spec.mjs:299` asserts *a save is never shown a position
  the reader did not stand at* and is green on a build that flashes for two
  thirds of a second, because localhost is the one profile where a deferred
  script wins the race by construction. 80 ms with 4 Mbps and 2× CPU would have
  caught it eight frames wide. A case that cannot fail is this tab's recurring
  failure, and this milestone has now produced it twice.
- **It costs no sign-in.** [F242](../deferred-findings.md#open) counts two spare
  against `LOGIN_RATE_PER_MIN`, so the emulation goes on the file's shared serial
  page rather than in a new context, and it is scoped and disposed the way that
  file's trail probe already is.

### The logo controls sit between the colours and the size

- **F246(b)**, owner-set: *"The logo upload thould be below the color pickers
  and above size."* **As this reopening finds it**, the logo controls are
  `partials/link_qr.html:719-748`, ahead of the style form at `:743`; the colour
  inputs are `:784` and `:789` and the size control `:848-862`. The position
  asked for is inside that form's grid, between them.
- **This reverses the constraint recorded one reopening ago, and why the old
  argument no longer applies is the whole of it.** *"It moves within the
  section; it does not move into the style form"* was written from two facts
  that are both still true — a file needs `enctype="multipart/form-data"`, and
  HTML forbids nesting one `<form>` in another. Neither is the whole rule. A
  form-associated control carries a `form="…"` attribute naming the form it
  submits to and may sit **anywhere in the document**: the nesting ban is on the
  `<form>` element, not on its controls.
- **Two things the build shows rather than assumes**, because that attribute is
  where this gets interesting. `hx-trigger="change"` sits on the form element at
  `:722`, and a control outside that element does not bubble `change` to it, so
  the trigger moves onto the input. And htmx serializing a form-associated
  control is a claim about htmx, demonstrated against the running instance
  rather than argued. If neither that route nor another one works, **that is a
  prompt** — not a quiet retreat to the position the tab already has.
  *Enforced by:* a template test asserting document order — the logo controls
  after the background colour input and before the size control — **and** a
  browser case uploading a logo from the moved control and finding it applied,
  because an ordering test cannot tell a working upload from a detached one.

### The size slider draws its stops

- **F246(c)**, owner-set: *"The Size slider should have visible detents at the
  stop points."* The stops are already on the page: `httpx/web_links.go:1236`
  lists eight, `qrSizeStops` filters them to the code's own floor, and
  `partials/link_qr.html:850-856` puts them in a `<datalist>` the slider names
  with `list=`. Chromium draws tick marks from that datalist, and
  `static/css/input.css:97-103`'s `appearance: none` removes them along with the
  native track. Verified 2026-08-15 by forcing `appearance: auto` on the shipped
  control with nothing else changed: eight marks appear.
- **Restoring the native appearance is not the fix.** `appearance: none` is what
  lets the track and the thumb take theme tokens, which the size control was
  given deliberately; handing it back trades the theme for the marks. The marks
  are drawn by this stylesheet, or by markup this template renders.
- **The difficulty is that the stops are neither evenly spaced nor the same for
  every code.** 128, 256, 300, 512, 600, 1024, 1200, 2048, against a floor that
  moves with the module count — so a fixed background pattern is wrong on most
  codes. A mark's position is `(stop − min) / (max − min)`, and CSS cannot
  compute it without being handed the numbers: a custom property the template
  writes, or rendered elements, are both available and the build argues its
  choice.
  *Enforced by:* a template test that the marks the page draws are exactly the
  list `QRSizeStops` carries — count and values — so a code whose floor drops
  the low stops does not draw them anyway, and a browser case asserting a mark
  is actually visible.

# M23 — Cross-replica cache invalidation (pub/sub)

**Depends on:** nothing. **Discharges:** the known limitation *Cache invalidation
is single-replica* (Plan.md).

Split from [M24](m24.md) deliberately: they were one milestone in the first draft
and two subsystems in one commit exceeds the one-milestone-per-commit rule.
Invalidation lands before [M34](m34.md) and [M40](m40.md), because routing rules
make a stale snapshot serve a disabled variant and custom domains make a stale
host record a security matter.

## Done means

- `InvalidateAlias` and `InvalidateRoot` publish on Redis pub/sub; every replica's
  subscriber clears its in-process tiers — both the alias memCache and the
  separate root-redirect cache.
- With Redis absent or down, behaviour degrades to today's TTL staleness, nothing
  errors, and the degradation is documented. A Redis-down integration test proves
  redirects and invalidation still work.
- A dropped subscriber connection reconnects and degrades to TTL in the meantime —
  never to silence mistaken for freshness. Tested.
- **On reconnect, both in-process tiers are flushed** (decision D20). Pub/sub does
  not replay, so invalidations published during the gap are unrecoverable and the
  replica cannot know which keys they named; flushing ends the stale window at
  reconnect rather than at each entry's TTL. A test proves an entry cached before
  the drop is gone after the reconnect, not merely expired later.
- The hostname cache [M40](m40.md) adds joins this mechanism; that dependency is
  stated there.
- SLO re-verified: the subscriber is off the request path, tripwire tests pass
  unmodified, cached p99 under 20ms.

## Reopened 2026-08-01 — the subscriber cannot tell silence from freshness

M23 shipped and the claim its Risks section calls *the whole risk* turned out
false. Reopened by the owner on [M32.9](m32.9.md)'s triage.

**What is false.** The bullet above says *"A dropped subscriber connection
reconnects and degrades to TTL in the meantime — **never to silence mistaken for
freshness**. Tested."* It is true for a **dropped** connection and false for a
**stalled** one. Against a Redis that holds the connection open and stops
answering, `ReceiveMessage` blocks with no deadline, `Run` never reaches its
error branch, `establish` is never called, and `flush()` never runs — so that
replica serves pre-edit destinations for the remaining entry TTL, up to
`REDIRECT_TTL` (24h default), with no error, no log line and no metric.
Recorded as [F30](../deferred-findings.md); the fix is in spec here.

Reproduced against real Redis behind a proxy that discards bytes while holding
both sockets open: **Redis reported delivering the invalidation to 1 subscriber
and it was silently lost**, `ReceiveMessage` stayed blocked for 40s, and
`establish`'s liveness ping returned `nil` in 0ms. The control — the socket
*cut*, which is the only shape the existing tests cover — errored in 0.1s and
recovered correctly.

**Two library facts the fix has to work around**, both verified at the pinned
go-redis v9.21.0: `ReceiveMessage` is a bare loop over `Receive` →
`ReceiveTimeout(ctx, 0)`, and a zero timeout with no context deadline resolves
to `noDeadline`, so `ReadTimeout` never applies on this path. And `PubSub.Ping`
is **write-only** — it writes the command and never reads a reply — so a `nil`
return proves only that bytes entered the socket buffer, which is why
`invalidation.go:238-240`'s claim that a successful ping means the subscription
is *"genuinely live rather than merely not-yet-failed"* is false.

### Done means, for the reopening

- **The read is bounded.** `ReceiveTimeout` with a non-zero duration, and a
  timeout treated as a re-establish trigger rather than an error to log. The
  bound is a new knob or a documented reuse of an existing one; either way it
  is in `docs/configuration.md`.
- **Do not reach for `Channel()`.** This is the trap: go-redis's higher-level
  API advertises a health check that periodically pings and re-subscribes, and
  `initHealthCheck` implements it with the **same write-only `Ping`** while
  `initMsgChan` reads with `context.TODO()`. Switching to it would look like a
  fix and change nothing.
- **`invalidation.go:238-240`'s comment is corrected.** It states a property the
  library does not provide, and it is the reason the gap survived review.
- **A test against the stalled shape.** `test/integration/invalidation_test.go`
  already has `proxy.stalled(true)` — built for M26.6 and pointed only at the
  writer. Every subscriber test uses `proxy.cut()` or `proxy.refuse(true)`. The
  new test asserts that a replica whose subscriber is stalled either reconnects
  within the bound or stops serving the stale entry, and it must fail against
  the current tree.
- **Single-replica deployments stay unaffected**, and the fix does not put the
  subscriber on the request path — M23's SLO re-verification bullet still holds.

## Risks

Reconnect semantics are the whole risk. A subscriber that silently stops
delivering looks identical to "nothing changed", which is the failure mode that
makes stale data invisible.

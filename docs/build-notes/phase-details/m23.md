# M23 — Cross-replica cache invalidation (pub/sub)

**Depends on:** nothing. **Discharges:** the known limitation *Cache invalidation
is single-replica* (Plan.md).

Split from [M24](m24.md) deliberately: they were one milestone in the first draft
and two subsystems in one commit exceeds the one-milestone-per-commit rule.
Invalidation lands before [M34](m34.md) and [M40](m40.md), because routing rules
make a stale snapshot serve a disabled variant and custom domains make a stale
host record a security matter.

## Done means

- `InvalidateAlias` and `InvalidateRoot` publish on Redis pub/sub; every replica's
  subscriber clears its in-process tiers — both the alias memCache and the
  separate root-redirect cache.
- With Redis absent or down, behaviour degrades to today's TTL staleness, nothing
  errors, and the degradation is documented. A Redis-down integration test proves
  redirects and invalidation still work.
- A dropped subscriber connection reconnects and degrades to TTL in the meantime —
  never to silence mistaken for freshness. Tested.
- The hostname cache [M40](m40.md) adds joins this mechanism; that dependency is
  stated there.
- SLO re-verified: the subscriber is off the request path, tripwire tests pass
  unmodified, cached p99 under 20ms.

## Risks

Reconnect semantics are the whole risk. A subscriber that silently stops
delivering looks identical to "nothing changed", which is the failure mode that
makes stale data invisible.

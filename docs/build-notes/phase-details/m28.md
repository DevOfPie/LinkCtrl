# M28 — Team management, workspaces, and org creation

**Depends on:** [M27](m27.md). **Discharges:** Collaboration scope row
*Organizations: sharing, invites, team management* (completes it), plus workspace
and organization creation added by decisions D15 and D16.

**Scope note.** Workspace CRUD and org creation are *additions*, not existing
scope rows — the Collaboration row is silent on both. They are here because
workspace-scoped roles otherwise have no second object to scope to (D15), and
because D6's membership-only invited user must be able to own an organization
later without a second account (D16). Recorded as deliberate added scope rather
than allowed to look original.

## Done means

### Members

- Member list, role change, and removal exist in API and UI, gated by
  `members.read` / `members.write` — now both enforced.
- Role assignment is rank-bounded: nobody grants a role binding tighter than
  their own. The rank semantics, including whether admins may manage admins, are
  written as a table in this file *before* code, then tested. Ambiguity here
  becomes a privilege-escalation bug.

  **The table, written 2026-08-01 at M28's validation, from decision D30 —
  before any code.** Ranks are `owner` 10, `admin` 20, `editor` 30, `viewer` 40;
  lower binds tighter. *Manage* means re-role or remove, and is gated by
  `members.write`.

  | Actor | May manage | May not | Why |
  | --- | --- | --- | --- |
  | **owner** (10) | owner, admin, editor, viewer — every rank, its own included | remove or demote **the last owner** | D30's single exception to *strictly below*. An owner already holds everything, so the escalation argument has nothing left to protect; the last-owner refusal is what stops an org being orphaned |
  | **admin** (20) | editor, viewer | **another admin**, and owner | Strictly below. An admin managing an admin is lateral, and lateral is how an admin removes the peer who would have stopped them |
  | **editor** (30) | nobody | — | Holds no `members.write` (`00700_seed.sql`) |
  | **viewer** (40) | nobody | — | Same |

  Two consequences worth stating because a test must pin them. An admin cannot
  demote *themselves* — self is not strictly below self — so an admin who wants
  out asks an owner. And "strictly below" is evaluated on rank, not on identity,
  so a second `owner` is managed by the first without either being special.
- Removing the last owner of an org is refused, tested.
- Workspace-scoped memberships (`workspace_id` set) are issuable and the evaluator
  resolves them — the COALESCE uniqueness and rank machinery from 00200 finally
  has a writer.

### Workspaces (decision D15)

- Workspace create / rename / delete within an org, permission-gated. Deleting a
  workspace that holds links is refused or requires explicit confirmation — the
  decision is recorded, not left to the implementation.

### Organizations (decision D16)

- A new `orgs.create` permission, with its seed migration and delegability
  decision.
- **Granted by default to self-registered users only.** On a default instance —
  where `closed` is the shipped ceiling and everyone else arrives by invite — that
  means the owner from the setup form, and nobody else until they grant it.
- Creating an org provisions it with a workspace and an owner membership, in one
  transaction, reusing the `Register` path's tenancy semantics rather than a
  second implementation of them.
- The permission is the call site a future entitlement check would hang on —
  **unscheduled**. Phase 3 declined commercial work as an area (D108) and it
  stays a candidate in
  [phase-3-candidates.md](../phase-3-candidates.md#g--commercial-and-entitlements-area-not-taken).
  Nothing in this milestone is billing-shaped.
  *(Amended 2026-08-10 at [M58](m58.md). It read "(Phase 3+, see Plan.md)",
  which describes unscheduled work as scheduled. This is the **second** of two
  anchors for one seam — the first is `CreateOrganization`'s doc in
  `internal/team/organization.go`, corrected earlier in the same milestone — and
  the candidates file's Area G close-out counted one. A count, so a fact.)*

- Member added / removed / re-roled, workspace created, renamed or deleted, and
  organization **created**, are all audit events ([M21](m21.md)).
  *(Amended 2026-08-01 at step 3.4. The bullet read "workspace and org created

## Reopened 2026-08-01 — the pages exist and cannot be opened

M28 shipped and its claim turned out false. Reopened by the owner rather than
succeeded, per [workflow.md](../workflow.md)'s rule, so the correction carries
this milestone's number and the trail stays in one place.

**What is false.** Two bullets above say member management and workspace
management exist in the UI. Both pages return **500 on a plain GET** as soon as
the acting organization has more than one workspace — which is the state M28
itself exists to create. Recorded as
[F20](../deferred-findings.md); the fix is in spec here.

### Done means, for the reopening

- **`/workspaces` and `/members` render** for an organization with any number of
  workspaces, and the workspace switcher renders **on them** — today it is
  silently absent from exactly the two pages that are about workspaces.
- **The trigger is stated precisely, because the obvious wording is wrong.** The
  condition is more than one workspace **in the organization currently being
  acted in**, not more than one in total: `team.Service.Workspaces` filters on
  `actor.OrgID` (`internal/team/workspace.go:60`), so a user holding six
  workspaces across two organizations sees 200 while acting in a
  single-workspace one. A regression test written as *two workspaces* without
  *in one organization* passes without the fix, which is the trap this bullet
  exists to close.
- **The validation path answers 422 again.** `renderWorkspacesError` re-renders
  the same page, so every form error on it — a duplicate workspace name, an
  empty one — currently surfaces as a 500 and its message is unreachable.
  Asserted by test, because this is the half that looks fixed once the page
  loads.
- **A test covers `/members` with a member who lacks `members.write`.**
  `loadMembersPage` returns early without assigning the field, so that path
  never hit the defect and would not have caught it.
- The root cause is a page struct field shadowing a shell field of the same
  name. Whatever the fix, **it is asserted by a test that fails if any page data
  struct in `internal/httpx` redeclares a field the shell already provides** —
  the mechanism, not a comment asking the next author to remember.

### Why the tests missed it

Worth writing down, because the gap is the reusable part.
`TestEveryPageRenders` builds each page's data from a fixture and renders it, and
the fixture supplies the shell's `Workspaces` with the type the shell declares.
Production supplies the page's own field, of a different type, and the template
resolves the page's field first. The test and the product therefore render two
different structs through the same template, and only one of them has ever
failed. A fixture that mirrors the handler's own construction is the thing that
would have caught it.

## Reopened 2026-08-01 — a workspace-scoped role reaches the whole organization

M28 shipped and a second claim turned out false, separately from the one above.
Reopened by the owner on [M32.9](m32.9.md)'s triage.

**What is false.** The *Two consequences worth stating because a test must pin
them* paragraph says **an admin cannot demote themselves — self is not strictly
below self**. Here self *is* strictly below self. An actor holding an
organization-wide `viewer` row (rank 40) and a workspace-scoped `admin` row
(rank 20) has an identity rank of 20, because `GetUserRoleInWorkspace` takes the
minimum; `mayManage(20, 40, 10)` is therefore true against **their own
organization-wide membership**, which comes back `IsSelf: true` and
`Manageable: true` at once. One dropdown on `/members` turns a workspace-scoped
admin into an organization-wide one. Recorded as
[F27](../deferred-findings.md); the fix is in spec here.

**The wider shape.** Permissions resolve per acting workspace while every write
they gate scopes by `actor.OrgID` alone, so the same actor can also `Grant`
themselves a role in any workspace in the organization, `ChangeRole` and
`Remove` organization-wide members, and issue an invitation whose redeemed
membership is organization-wide. A workspace-scoped **owner** additionally holds
`org.delete` — `resolveRole` refuses only `role.Rank < actor.RoleRank`, so
`10 < 10` is false and an owner may grant owner scoped to one workspace, and
`Roles` offers it. `internal/team/workspace.go` already does the right thing for
`workspace.write` via `canInWorkspace`, with a comment naming this exact
attacker; no member operation calls it.

### Done means, for the reopening

- **The self-promotion route is closed, and closing `Grant` does not close it.**
  This is the trap: a fix confined to `Grant` leaves the one-dropdown route
  wide open, because that route calls no `Grant` at all. Both are in spec.
- **A membership's authority is bounded by the membership that carried it.**
  `members.sql:69-71` already states the rule the code does not enforce — *"a
  workspace-scoped owner membership grants ownership of one workspace, not of
  the organization"* — and `LockOrganizationOwners` already filters
  `m.workspace_id IS NULL` for exactly that reason. Whatever mechanism is
  chosen, it makes that filter's reasoning true on the authorization side too.
- **`refuseLastOwner` covers promotion, not only demotion.** Today it fires only
  when `member.RoleSlug == "owner" && role.Slug != "owner"`, so an escalated
  actor can promote their own row to owner and then remove the real one.
- **The UI stops offering what the server refuses.** `members.html:33-39` ranges
  over all of `.OrgWorkspaces` with no filter on `Manageable`, which is why the
  escalation is three dropdown picks rather than a forged request.
- **Tests use a workspace-scoped actor as the actor of a write.** Every
  `Grant`/`ChangeRole`/`Remove` in `team_test.go` passes `f.owner`; the one
  workspace-scoped identity the suite builds is only ever read. That is why the
  suite is green against all of this.

## Risks

The rank table is the security surface. Write it first. `orgs.create` defaulting
to self-registered-only must be expressed as a grant at account creation, not as
a runtime check against how the account was made — the latter is a second
authorization axis alongside RBAC, which is what D16 chose to avoid.

Reopening adds one: the fix is a type change on two page structs, and the
milestone that first rendered those pages is also the milestone whose tests
passed while they were broken. Fixing the shadowing without fixing the fixture
leaves the next field with the same name free to do this again.

# M38 — Folders: API and tree UI

**Depends on:** nothing. **Discharges:** Link-management scope row *Folders — API
and tree UI*. The table has existed since Phase 1 with no queries, service, API or
UI.

## Done means

- Folder CRUD and a move operation exist.
- **A folder can never become its own descendant** — cycle test. *(True of one move and false of two, until the reopening below.)*
- Sibling-name uniqueness and a depth cap are enforced in the service, with the
  decision recorded. *(Enforced against a snapshot no lock protected on the
  create path, until the second reopening below.)*
- Deleting a folder leaves its links intact via the existing `SET NULL` semantics,
  tested. Losing links because a container was deleted is the failure this names.
- Links are assignable to folders in API and UI; the links list filters by folder.
- The tree UI is progressive-enhancement htmx: click-to-move via POST forms, **no
  custom drag-and-drop JavaScript**, works without JS. Drag-and-drop is
  deliberately out unless asked for.
- Permission decision recorded: reuse `links.*`, or a new `folders.*` with its seed
  migration and delegability call.

## Risks

Low. Tree rendering depth and move semantics are the only design surface.

## Reopened 2026-08-05 — two moves that each passed the check the other broke

[F108](../deferred-findings.md), found by [M44.9](m44.9.md) and approved on
[M45](m45.md)'s third triage. Reopened rather than fixed inside M45 because it is
this milestone's own claim that was false, and workflow.md's rule keeps the
correction under the number that made it.

### What was wrong

> A folder can never become its own descendant.

True of one move. `MoveRefusal` answers *is the new parent inside the subtree
being moved* — a question about the whole tree, which cannot be written as a
column check — and it was computed from a tree read on its own connection, then
acted on outside that read. So two moves a few milliseconds apart each passed a
check the other invalidated: A under B while B moves under A satisfies both, and
the pair detaches from the root, reachable from nothing and unfixable through the
UI because every move of either one is now refused.

The cycle test the bullet names exercises one caller. Nothing exercised two.

### What changed

`MoveFolder` reads, decides and writes in one transaction, over the workspace's
folders locked by `LockWorkspaceFolders` in a fixed id order. The whole workspace
rather than the two folders named, because a cycle can run through folders
neither move mentions; the fixed order because two transactions taking the same
locks in different orders deadlock where a shared order makes them queue — the
reasoning `LockOrganizations` already wrote down.

### How it is tested, which is the part worth reading

Not by racing goroutines. [F67](../deferred-findings.md) established in this same
milestone that the window is tens of microseconds and that racing loses against
it, and that merely holding a row proves nothing when the write blocks on that
row anyway.

The test moves the tree **under** a request already parked on the lock: A→B is
issued and blocks, B→A is committed by the holding transaction, and the parked
move resumes against a tree in which its destination is now inside its own
subtree. Re-reading refuses it; not re-reading writes the cycle. Against the
shipped code both folders walk up to the recursion bound — each is its own
descendant, which is exactly what the bullet says cannot happen.

## Reopened 2026-08-06 — the create path never took the lock the move path learned to

[F149](../deferred-findings.md), found by the Fable 5 review on PR #4 and
approved for fix the same day. The first reopening brought `MoveFolder` under
`LockWorkspaceFolders` because the cycle rule is a question about the whole
tree; `CreateFolder` asks two whole-tree questions of its own — the depth cap
and the folder count — and kept deciding them from a tree read on the plain
pool, then inserting outside any transaction.

### What was wrong

> Sibling-name uniqueness and a depth cap are enforced in the service, with
> the decision recorded.

The sibling name was safe — the unique index holds it under interleaving. The
depth cap and the count cap had nothing: no lock, no transaction, no backing
constraint. The depth predicates differ between the paths — create asks about
the parent's depth, move about the subtree's reach — so a create under a leaf
racing that leaf's move deeper passed both checks while their composition
landed a folder past `MaxFolderDepth`, a state `MoveRefusal` will refuse to
ever produce but that then existed. Two creates at one below
`MaxFoldersPerWorkspace` both passed. Blocking was not the missing piece: a
nested insert already waits on its parent row behind a move's `FOR UPDATE` and
then proceeds on the decision it made before waiting, and a root-level insert
waits on nothing at all.

### What changed

`CreateFolder` now reads, decides and writes inside one transaction holding
`LockWorkspaceFolders` — F108's exact shape, extended from the path that
learned it to the path that needed it. The file header's rules name the lock
as what holds the two caps under interleaving, the way the sibling bullet
names the index. `RenameFolder` and `DeleteFolder` stay lockless deliberately:
rename's only tree check is index-backed, and delete only lowers the count.

Three tests, all parked-on-the-lock per F108's fix note (racing goroutines
never hit the window; what discriminates is driving the second operation under
one already holding the lock): create-vs-move on the depth cap, create-vs-
create on the count cap, and the count cap's first serial test anywhere —
folder 500 allowed, 501 refused, deletion reopening a slot. Sabotage-verified
by removing the lock call: the parked choreography then never completes, which
is the test refusing to pass against the unlocked path.

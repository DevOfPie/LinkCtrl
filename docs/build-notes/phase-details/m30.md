# M30 — Destination blocking: tiers and logging

**Depends on:** [M21](m21.md). **Discharges:** Link-management row *Malicious
destination blocking, tiered by confidence*; the tiers and logging legs of the
Security blocking row. Plan.md mandates these ship before disputes.

Two threat models wear one name. Phase 1's refusals protect *this instance* from
being an SSRF proxy. This milestone protects *visitors* from a destination hostile
to them. They must not share an override switch.

## Done means

### The three tiers

| Tier | Contents | Overruled by |
| --- | --- | --- |
| Unappealable | Phase 1's SSRF refusals, untouched | Nothing |
| High confidence | Curated embedded exact-host list, shipped like `reserved.txt` | Editing the list and rebuilding |
| Low confidence | Heuristics + a runtime-mutable Postgres blocklist | The instance owner, from the review queue |

- A test asserts **no configuration, list entry, or future review path can accept
  a metadata or private address**. The unappealable tier shares no override switch
  with anything.
- Heuristics never write into the embedded tier — asserted structurally, not by
  convention. Confining that tier to exact matches is what keeps a false positive
  there from costing a rebuild often enough that operators route around it.
- Low-confidence heuristics: punycode homographs, credentials in the URL,
  shortener chains. **Freshly-registered domains is excluded** (decision D13): it
  needs a domain-age data source, which means egress, which collides with the
  no-destination-leaves-the-box promise. Noted as exactly what [M32](m32.md)'s
  opt-in feed path can supply. The scope row is annotated rather than silently
  shipped short.
- `LINKCTRL_DESTINATION_BLOCKLIST` seeds the runtime Postgres list and keeps
  feeding it — the env list keeps working.
- Every refusal's 422 carries a reason code naming its tier and rule.

### Coverage and logging

- The check runs at every destination-writing surface that exists when this ships:
  link create, link update, and the root redirect — all three `ValidateDestination`
  call sites, kept by test. Re-checking already-accepted links is **not** included
  (Plan.md calls it a separate job and a separate decision).
- **Every later milestone that adds a destination-writing surface declares this
  one as a dependency and passes the full tier check**, asserted by its own tests:
  [M34](m34.md) rule destinations, [M36](m36.md) split-test variants,
  [M42](m42.md) webhook targets. This closes the bypass the plan review found in
  two of three candidate orderings.
- Every blocked attempt writes an audit event with `ip_prefix` and the attempted
  URL stored as evidence. Wherever that URL is displayed it is escaped and
  defanged — a test plants a `javascript:` URL and an HTML-bearing URL and proves
  both render inert.
- Blocking runs only on the management path. The redirect tree is untouched and
  its tripwire tests pass unmodified.

## Reopened 2026-08-01 — one character defeats the tier that has no override

M30 shipped and its strongest claim turned out false. Reopened by the owner on
[M32.9](m32.9.md)'s triage rather than succeeded, per
[workflow.md](../workflow.md)'s rule, so the correction carries this milestone's
number.

**What is false.** The bullet above says *no configuration, list entry, or
future review path can accept a metadata or private address*. A **trailing dot
on the hostname** accepts one. `POST /api/v1/links` with
`http://169.254.169.254./latest/meta-data/` answered **201** on a live instance
while the dotless form answered 422; `127.0.0.1.`, `10.0.0.1.`, `2130706433.`,
`0x7f000001.`, `localhost.` and `foo.localhost.` all behave the same way, and
the high-confidence embedded list is defeated identically —
`metadata.google.internal.` is accepted although that exact host is in
`blocked_hosts.txt`. `PATCH` is affected too, the stored value is 302'd verbatim
at serve time, and **no `destination.blocked` audit row is written**, so nothing
records the attempt. Recorded as [F26](../deferred-findings.md); the fix is in
spec here.

**What it is, and is not.** It is a stored **open redirect**, not SSRF.
LinkCtrl never makes a server-side request to a destination — the only two
`http.Client`s in the tree are the opt-in feed and the container healthcheck —
so the victim's own browser makes the request and the attacker cannot read the
response. That is why this reopens M30 at *high* rather than critical, and the
distinction belongs in the fix's own reasoning.

### Done means, for the reopening

- **The dot is canonicalised away, not rejected.** `destination_test.go:133`
  asserts `https://example.com./` is **accepted**, and it is right to: a
  trailing dot is a fully qualified name, not a malformed one. A fix that
  refuses dotted hosts breaks a passing test for the wrong reason.
- **One normalisation point, covering all three tiers.** The DB tier already
  trims (`HostCandidates`, `blocking.go:298`) and `checkListEntry` already
  refuses a dotted *entry* — so today the write side normalises and the read
  side does not. Folding the host once in `ValidateDestination`, before the
  address, numeric and localhost checks, closes the unappealable tier and the
  embedded lookup together; a second hand-written trim in a third place is the
  shape that produced this.
- **A test that feeds a trailing-dot host to each tier.**
  `TestUnappealableTierHasNoOverrideSwitch` walks `DestinationPolicy` by
  reflection looking for a *field*; it never tries a *host*, which is why a
  promise about what can be accepted was guarded by a check on struct shape.
  The new test asserts refusal for the metadata address, a loopback literal, an
  obfuscated numeric form, `localhost.` and an embedded-list host, and asserts
  `https://example.com./` still passes.
- **The audit consequence is covered**: a refused dotted host writes its
  `destination.blocked` row like any other refusal.
- `blocking_test.go:441-444` already asserts this exact class for the Postgres
  tier, calling it *"a one-character bypass"*. The class was known and fixed in
  one of three places; say so in the commit rather than presenting it as new.

## Risks

Heuristic false-positive rate is unknown until real use; reason codes and
[M31](m31.md)'s queue are the mitigation. The embedded list's initial contents
need owner sign-off.

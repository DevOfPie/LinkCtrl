# M64 — An add-on reaches the page: routes, templates, config

**Depends on:** [M62](m62.md) *(hard — routes are a declared permission)*;
[M63](m63.md) *(ordering — a page with nothing to read is a demo, and the demo
should wait one milestone rather than fake its data)*.
**Discharges:** the routes, templates and config limbs of the reach answer
(*everything OIDC needs*,
[phase-4-candidates.md](../phase-4-candidates.md#the-answers-that-set-its-shape)),
and makes the named `ui`-collision argument in writing.

OIDC needs a place to start a flow and a callback to land on; any useful add-on
needs configuration. This milestone gives an add-on HTTP routes on the
dashboard tree and a way to render pages — inside the CSP, without moving it.

## Done means

- **A declared route prefix mounts**: an add-on holding the routes grant gets
  `/addons/<name>/…` on the **app tree only** (`registerAppRoutes`,
  `internal/httpx/router.go` — the `appMux`), never on the link tree. The
  redirect tree's tripwire tests
  (`test/integration/redirect_test.go`, `tripwireAuthenticator`) pass
  unmodified; a test asserts an add-on route registered on the link host 404s.
- **The CSP does not move** — the inherited rule argued in writing, as
  [phase-4-candidates.md](../phase-4-candidates.md#what-this-collides-with-named-now-rather-than-discovered)
  requires: `internal/httpx/middleware.go`'s `csp` constant is byte-identical
  before and after, asserted by test. An add-on renders through host-side
  templating — it returns content the host wraps in the layout
  (`internal/ui/templates/layout.html`), or serves declared static assets from
  its module through the host's handler; it cannot inject script tags, inline
  handlers, or external references, and a test module that tries renders
  inert text.
- **Both themes hold**: add-on pages inherit the M24.5 theme tokens through
  the host layout, and the theme test's discipline
  (`internal/ui/theme_test.go`) covers whatever host-side CSS this milestone
  adds. **The scan cannot see add-on assets** — it walks the embedded
  templates, and a module's assets are not in the embed — so this milestone
  either extends the same discipline to served add-on CSS as a host-side
  check, or ships add-on CSS unscanned and says so in this file and in the
  manager's surface. Which, is this milestone's design work; pretending the
  existing scan reaches it is not an option, and this sentence exists so that
  gap is a decision rather than a discovery.
- **Config reaches an add-on the way it reaches the product**: keys under
  `LINKCTRL_ADDON_<NAME>_…` are read through the same env mechanism
  (`internal/config`), handed to the module at load, readable through the
  M61 config host function, and bounded by the config-keys grant. Secrets get
  the `Secret` treatment — an add-on's client secret must not print, same as
  the host's own. Manifest-declared settings (M60) arrive through the same
  host function; *editing* them is [M68](m68.md)'s page, never the
  environment and not this milestone.
- **Session context, not session power**: an add-on route handler can ask the
  host *who is signed in* (identity, workspace) when its grant includes it; it
  cannot read the cookie, mint, or destroy sessions — that boundary is M65's
  subject and stays closed here, asserted by the ABI having no such function
  yet (M61's declared-but-refused list). *(Amended 2026-08-30 at
  [M69.9](m69.9.md) — a fact, not the assertion. The bullet is still true of what
  M64 delivered, and its own "here"/"yet" said so: at M64's terminal commit
  `c0d0025` the ABI carried `session_mint` with no `Live` field. M65 set it
  `Live: true`, so a reader following the cross-reference today finds a
  declared-but-refused list holding only `template_render`. The amendment rather
  than a reopening follows [D304](../decisions.md), which ruled the same way on
  M62; M65 wrote the matching parenthesis into m60.md and not into this file.)*
- **Deliberately not done:** add-on entries in the nav
  (`internal/ui/templates/partials/nav.html`) — M68 decides how installed
  add-ons are presented, and until then an add-on's pages are reachable by URL
  and from the manager (M68); WebSocket/SSE anything; and add-on routes on the API
  tree under `/api/v1` — every UI feature has API support is a *product* rule,
  and whether it binds third-party surfaces is a question M69 will force with
  a real case rather than this milestone deciding in the abstract.

## Risks

- Host-wrapped rendering is the load-bearing security claim, and template
  escaping across a host/guest boundary is subtle — the escaping context must
  be chosen by the host, with the add-on's output always data, never template.
  Adversarial tests with hostile output are in scope from day one.
- WASM route handlers hold an instance per request or a pooled instance;
  either choice has a cost profile this milestone measures (dashboard target
  is <250ms, unmeasured — this must not be what finally breaks it).
- The `/addons/` prefix collides with nothing today, verified against
  `registerAppRoutes`; the reservation still needs a test so a future product
  route cannot take it back silently.

## What this milestone answered

The three questions this file leaves to the milestone, answered here because two
of its own bullets say the answer belongs in this file. Full reasoning, options
and costs are in [decisions.md](../decisions.md); this is the record a reader of
*this* file needs so the bullets above are not left looking open.

**The theme gap: no add-on CSS is served at all** — D264. The bullet offers a
disjunction, *"returns content the host wraps in the layout, **or** serves
declared static assets from its module"*, and this milestone takes only the first
limb. So there is no served add-on asset of any kind, the one template M64 added
is embedded like every other, and M24.5's scan therefore covers every stylesheet
this product serves with no exception to remember. The gap is closed by absence
rather than by a new check: building a scanner over third-party bytes while no
add-on ships any would be a filter whose first real input arrives in a later
milestone. What M68's surface owes is one sentence — an add-on's pages are drawn
with LinkCtrl's own layout and it ships no assets — and `Plan.md`'s limitation row
carries the same fact for a reader outside this directory.

**Rendering: the host owns every byte of HTML, and `template_render` stays
refused** — D259. An add-on returns text; the content types it may name exclude
`text/html`; the host wraps and escapes. That satisfies *renders through
host-side templating* and the *output is always data, never template* rule the
first risk states, and it leaves the ABI carrying a declared function whose
`BackedBy` names this milestone. That mismatch is [F283](../deferred-findings.md#open)
and is the owner's: redefining, moving or deprecating that function are each
changes to a published contract.

**One instance per request, at about two milliseconds** — D260, measured by
`TestRoutingCostsAnInstantiation` rather than inherited from M60. The second risk
asks this milestone not to be what breaks the unmeasured 250 ms dashboard target,
and the answer is a test that fails at a tenth of it. What the choice buys is that
guest memory does not cross requests; what it costs is memory per request in
flight, which is why the number in flight is bounded at sixteen. The 2.4 MB this
paragraph used to give as that cost is a **measurement of a fixture** and was
never a bound — [the reopening](#what-the-reopening-corrected-f289-and-f290) is
where that distinction cost something and where the bound now is.

**One thing no bullet asked for, in scope by a standing rule.** Two add-ons whose
names stand in a `name + "_"` prefix relation shared both namespaces derived from
those names: add-on `oidc` may declare the cookie prefix `oidc_x` and then read and
overwrite every cookie of add-on `oidc_x`, session state included, and
`LINKCTRL_ADDON_OIDC_X_KEY` is a setting of each. Measured with both loaded, and
three sentences — one of them a passing test — asserted it could not happen.
[workflow.md](../workflow.md#standing-rules): *a recorded abuse path is in a fix
milestone's scope by default … including when it is found during that milestone*.
The refusal is at load, in `nameCollisions` (`internal/addon/host.go`), and it closes
the cookie case and the settings case with one check because both namespaces are the
name with a separator and something joined onto it. D267 records what was measured,
why **both** names are refused rather than one, and the six sentences corrected
against the three the review listed.

**Two things this file did not put in scope and this milestone still had to
decide.** Add-on routes are **public** (D261), because a session requirement would
make M65's hook unreachable through the surface built for it — and the *session
context* bullet's "when its grant includes it" is what F270 said had nowhere to
arrive, so the grant is a new token (D258). The demo shows no add-on page, and
D265 records why: an add-on is files rather than rows, `demoCoverage()` is SQL
only, and shipping a wasm module into the demo image is a decision about what the
demo is.

## What the reopening corrected: F289 and F290

M64 shipped and came back. Two findings from M64.9's adversarial review falsified
claims made above, the owner approved the reopening as D269, and the work is
recorded here under M64's own number rather than in a successor milestone,
because the trail belongs in one place.

**F289 — an add-on could sign the visitor out, and the *Session context, not
session power* bullet said it could not.** That bullet's *it cannot read the
cookie, mint, or destroy sessions* was true of everything it was checking and
false of something nobody was checking: an add-on holding **only**
`routes.own_prefix` set 180 cookies inside its own declared namespace, the
browser's per-domain cap overflowed, and the eviction took `linkctrl_session`.
Reproduced twice in real Chromium against a real signed-in account — n=179 stays
on `/dashboard`, n=180 lands on `/login?next=/dashboard`. Narrower than *destroy
sessions* reads, and worth stating precisely because the fix is judged against
it: the server-side session survives, the token stays valid, the add-on never
learns it, and what was achieved was a forced **client-side** sign-out, repeatable
on every visit, from the cheapest grant this milestone hands out.

The bullet now stands as written, and it stands structurally rather than by a
filter. The host writes no cookie a module named: it packs an add-on's cookies
into one cookie of its own per lifetime class, `Route` empties the module's list
as it packs, and the writer in `internal/httpx` has no path to that list at all.
An add-on's occupancy of a browser's cookie store is therefore fixed by the code
and does not move with what it sets or how often it is visited. **Why it is not a
count, a header-size bound, or any other threshold** — a browser cookie is
persistent and the add-on also decides how many responses there are, so every
threshold is one it sits under and repeats — is D287, along with the one
threshold that remains, the 3 KiB an add-on may keep for itself.

**F290 — the concurrency bound priced an amount the add-on chose.** The runtime
carried no `WithMemoryLimitPages`, so wazero's 4 GiB-per-instance default applied
and *about 2.4 MB per request in flight* was a typical cost being read as a
bound. One request allocating 512 MiB took the host from 78 MB resident to
1604 MB; sixteen concurrent reached 4332 MB, against a documented floor of 1 GB.
The figure itself was never wrong — a fixture measures 2.31 MiB at load — which
is why the correction is to the *kind* of sentence and not to the number.

An instance now gets 128 pages, 8 MiB, set on the runtime so every instance this
host makes is bound by it. Sixteen in flight times 8 MiB is the **128 MiB**
ceiling `docs/SECURITY.md`, `docs/deployment.md`, `docs/configuration.md` and
`CHANGELOG.md` state, and a test holds **each of the three numbers** against
every sentence that states one — in those four files, in `Plan.md` and
`docs/operations.md`, and in the two publisher-facing ones that give the
per-instance bound, `docs/addon-abi.md` and `sdk/doc.go`. Not their product,
which is what the first attempt at this tie checked and which thirty-two
instances of 4 MiB would have satisfied without a word of any of them changing.
**Which sentences those are is swept rather than listed from memory**, which took
a third pass and is [below](#what-the-third-pass-corrected). What the bound
bounds is *live* guest memory rather than resident size, and `docs/deployment.md`
says so with the measurement rather than implying otherwise. D288 carries why
eight rather than sixteen — 4 MiB allocates, 5 MiB traps, on the fixture the
standard toolchain produces — and what the bound does not close.

**Neither finding changed what this milestone is for.** Both were bounds missing
from surfaces the bullets above already described, and both are now properties of
the code that a later milestone would have to remove deliberately rather than
forget.
## What the second pass corrected: D289

The reopening came back once more. The jar and the memory ceiling were sound and
both stayed; what came back was **three sentences claiming more than anything
checked**, which is the shape the reopening existed to fix, plus a bound that was
not total. D289 has the measurements and the reasoning; this is what a reader of
*this* file needs.

**The tie above now pins the parts.** Stated in its own paragraph rather than
here, because that is where the false version was.

**One published sentence was simply wrong, and the fix was the sentence.** *A
module whose memory section declares more than the bound is refused at load*
shipped in `CHANGELOG.md`, `docs/SECURITY.md`, `docs/addon-abi.md` and
`sdk/doc.go`. Measured against wazero v1.12.0: a declared **minimum** over the
bound is refused, and a declared **maximum** over it is **not** — the decoder
substitutes the runtime's own limit for it, so the module loads and its instance
is held to 8 MiB regardless. The behaviour is the one worth having, so the four
documents changed rather than the load path, and
`TestWhatAMemorySectionMayDeclare` measures both limbs on wasm written by hand —
the Go toolchain emits no maximum at all, which is why no fixture here could
have shown either.

**A cookie's `max_age` is bounded at 400 days, refused rather than clamped.**
`time.Duration` is int64 nanoseconds, so above about 9.2e9 seconds the expiry
arithmetic wrapped: `max_age=10000000000` produced an expiry before `now` and the
module was answered 200. The published ABI settles the shape — every bound on
that record is *ErrInvalid rather than a silently corrected response* — so the
refusal is at the module's own call. It is also the *Session context, not session
power* bullet's neighbour rather than its subject: nothing here was reachable
across add-ons, and what it cost was the add-on its own cookie.

**And the jars are merged rather than assigned**, so a jar a visitor plants at a
broader path no longer shadows the host's own for good.

## What the third pass corrected

Three findings against the second pass's own tree, none of them a new subject and
all three the same subject as the pass before: a sentence claiming more than the
thing beside it holds. D289 was corrected in place rather than superseded,
because none of it had been committed.

**The tie's *every file* claim was one file short, and the missing file was one
this change had itself edited.** The check listed eight sentences in six files
and claimed to cover every file outside build-notes that states any of the three
numbers. `Plan.md`'s limitation row states all three; `docs/operations.md`'s 503
row states the concurrency; and four of the six listed files state one of the
numbers a second time in a sentence no anchor covered. Seventeen sentences, not
eight. The nine missing anchors are added, and — because this is the second time
*every file* has been asserted by a person having read every file —
**the claim is now swept**: `TestEveryDocumentedNumberIsTied` finds every
occurrence of any of these numbers in the documentation and fails on one the
anchor table does not account for, either as a sentence tied to a constant or as
an occurrence about something else that says what. A new sentence quoting one of
these numbers costs one line here, and no line is a failing test.

**The margin under the 400-day cookie bound is 266x, not four orders of
magnitude.** `maxCookieAge` is 3.456e7 seconds and the int64-nanosecond overflow
is at 9.223e9. The bound is still comfortably total; the sentence justifying it
was not the sentence the numbers support.

**A jar could outlive everything in it.** `jarCookies` packed the kept jar with
eviction and then computed the cookie's `Max-Age` from the list before eviction,
so a 400-day value — the oldest, and therefore the first evicted when a jar
fills — left its lifetime on a cookie that no longer carried it, which is exactly
the *cookie a browser keeps in order to hand back nothing* that `jarMaxAge`'s own
comment says must not happen. Nothing crossed a boundary and nothing was
disclosed; the code made the sentence beside it false. `packWithEviction` returns
the survivors now, so there is no pre-eviction list at the call site to reach
for.

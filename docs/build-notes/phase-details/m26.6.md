# M26.6 — Bounded Redis failure, when the server never answers

**Depends on:** nothing. The edges to [M32.5](m32.5.md), [M34](m34.md) and
[M40](m40.md) are *ordering preferences*: each either measures latency or builds
more invalidation surface, and all of them are better done on top of a client
whose worst case is known. **Discharges:**
[deferred-findings.md](../deferred-findings.md) F2, owner-approved 2026-07-31.
Nothing on the scope tables.

A Redis that refuses a connection fails in 264ms. A Redis that *accepts* the
connection and then never speaks stretched a link edit to **9.07s**, measured
during [M23](m23.md) against a blackholing TCP proxy. `HTTP_REQUEST_TIMEOUT` is
15s, so an edit made during a stall comes within a few seconds of failing
outright — and a stall is exactly when an operator is most likely to be changing
things.

The phase's inherited rule is that Redis absent or down degrades behaviour and
nothing correctness-critical depends on it. *Stalled* is a third state, and it is
the one nothing was written against.

## What the tree says now

Recorded here because the fix is not the one F2 proposed, and the difference
matters. F2 attributed the 9s to go-redis not honouring the per-attempt context.
The arithmetic points somewhere else:

| Layer | Value | Where |
| --- | --- | --- |
| Outer retry loop | 3 attempts | [`resolver.go`](../../../internal/redirect/resolver.go), `deleteFromRedis` |
| go-redis internal retry | 3, its default — **`MaxRetries` is never set** | [`redis.go`](../../../internal/platform/redis/redis.go), `Open` |
| `REDIS_DIAL_TIMEOUT` | 1s | [`config.go`](../../../internal/config/config.go) |
| `REDIS_READ_TIMEOUT` | 50ms | same |

3 × 3 × 1s = 9s, against 9.07s measured. Two retry layers multiplying, over a
dial budget twenty times the read budget beside it.

## Done means

- **The mechanism is measured, not assumed.** The table above is a hypothesis
  until the milestone confirms it by attribution — which layer contributes what —
  against the blackholed proxy already available as
  `redisProxy.blackholed(true)` in `test/integration/invalidation_test.go`. If
  the arithmetic is wrong, the finding is corrected and the correction is
  recorded; a fix aimed at the wrong layer would leave the defect and remove the
  evidence.
- **A total budget exists and is enforced**, rather than a per-attempt one that
  multiplies. Invalidating an alias against a stalled Redis completes within a
  stated bound; the bound is a number in the milestone's decision entry, chosen
  against `HTTP_REQUEST_TIMEOUT` rather than picked for feel.
- **Asserted by test at the boundary that matters**: an edit against a
  blackholed Redis returns within the bound, and the edit itself still succeeds.
  Correctness never depended on the cache and must not start now — a bounded
  failure is still a failure to invalidate, and the existing log line saying the
  previous destination may be served until TTL stays.
- **The redirect path is checked for the same compounding, and the answer is
  written down either way.** `MaxRetries` and the dial timeout are client-wide,
  so they apply to the hot path too. The comment at `redis.go` claims a stalled
  Redis "costs a little latency and then falls through to Postgres"; if
  compounding retries make that false, it is a shipped claim that is false and
  fixing it is in spec here. If an established pooled connection makes it true,
  that is recorded as the reason rather than left as an assumption.
- **If the redirect path changes at all**, the [docs/slo.md](../../slo.md) k6
  measurement is re-run on the built image and cached p99 stays under 20ms, per
  the inherited rule. If it does not change, the milestone says so explicitly so
  the next reader knows the omission was decided rather than forgotten.
- Any new or changed configuration variable takes effect, is documented in
  [configuration.md](../../configuration.md), and appears in `.env.example` —
  the discipline every other setting follows.

## Deliberately not in this milestone

- **No change to what a failed invalidation means.** It still logs and still
  leaves the entry to expire by TTL. Making invalidation durable — an outbox, a
  retry queue — is a different milestone with a different claim, and reaching for
  it here would turn a timeout fix into a delivery-guarantee feature.
- **No circuit breaker.** Tracking Redis health across requests to skip calls
  during an outage is a real technique and a real amount of state; the bound
  above makes the worst case acceptable without it. Named here so its absence
  reads as a decision.
- **The 404-probe limiter stays per-instance.** It is listed in Plan.md's *Not in
  Phase 2* for reasons that have nothing to do with this.

## Risks

The measurement is the risk. A blackholed proxy is one shape of stall; a server
that answers the handshake and then hangs mid-command is another, and a fix
tuned to the first may not bound the second. The milestone should say which
shapes it tested and which it did not, rather than claiming a general result from
one proxy.

Lowering timeouts trades a stalled-Redis bound against false negatives on a
merely slow one. A dial budget cut too far makes a healthy-but-loaded Redis look
down and pushes load onto Postgres, which is the failure this would be
introducing in exchange for the one it removes. Both defaults are already
operator-tunable, which is the mitigation, but the shipped default is a judgement
and belongs in the decision entry with its reasoning.

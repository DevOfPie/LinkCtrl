# M26 — Mailer: optional SMTP delivery

**Depends on:** nothing. **Discharges:** decisions.md's statement that "every one
of signup's supporting features — invitations, membership in someone else's
workspace, a mailer — is Phase 2" (decision D1).

Lands before its consumers so email is integrated from each feature's first
commit rather than retrofitted.

## Done means

- SMTP delivery is configurable and **off by default**. An instance with no
  mailer configured behaves exactly as it does today, tested.
- Configuration follows the existing discipline: documented in
  [configuration.md](../../configuration.md), every variable takes effect,
  connection details validated at boot with a clear failure mode.
- Sends happen **off the request path** with bounded retry. The delivery
  mechanism — a scheduler job over a small outbox, or direct-with-retry — is a
  recorded decision. The redirect tree is untouched either way.
- Message bodies are plain-text-first, owned by the `ui` package's conventions
  (stdlib-only), and every mail renders untrusted input inert — the same
  hostile-input stance as the review queue.
- With the mailer unconfigured, **every consumer degrades to its mail-free
  behaviour rather than erroring**, tested. This is the claim that keeps the
  mailer optional rather than quietly required.

## Consumers

Specified in their own milestones: emailed invitations ([M27](m27.md)), address
verification gating `open` signup ([M29](m29.md)), emailed dispute outcomes
([M32](m32.md)), audit-growth alerts ([M21](m21.md) threshold, [M22](m22.md)
notification).

## Risks

The SMTP configuration surface — TLS modes, auth mechanisms — invites scope
creep. Ship the minimal honest set and document what is not supported rather
than implying universal compatibility.

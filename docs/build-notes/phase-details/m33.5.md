# M33.5 — A demo that shows the phase, not just its links

**Depends on:** [M32.9](m32.9.md). The edge is an *ordering preference* and it is
the owner's: the review comes first, and this lands after it. There is no code
dependency — every feature it seeds shipped at or before
[M32.5](m32.5.md).
**Discharges:** nothing on the scope tables. Owner-added scope, 2026-08-01,
from a `/note` observing that the demo has not grown since Phase 1 seeded it.

`lctl demo` fills an instance with a workspace, about twenty links and a few
weeks of click traffic. That was the whole product when it was written. Since
then Phase 2 has shipped invitations, members, workspace and organization
management, notifications, an audit trail, destination blocking, a dispute queue
and bot blocking — and somebody opening the demo sees none of it, because the
seeder produces no rows for any of them. The demo is the instance this project
tells people to look at, and it currently under-sells the phase it exists to
show.

## Done means

### What the seeder produces

Each of these is a row a person evaluating this instance can actually reach
through the product, not a fixture. That is the dashboard for all but one of
them — the audit log has no page and is read at `GET /api/v1/audit`, which is
deliberate and is what [README.md](../../../README.md) documents:

- **A second and third account, and memberships**, so the members page has more
  than one row and the rank rules from [M28](m28.md) have something to act on —
  including at least one non-owner, so *manage only strictly below your own
  rank* is visible rather than theoretical.
- **A second workspace with links of its own**, so the switcher
  [M25](m25.md) built has something to switch between and the scoping is
  observable. Today's demo has one workspace, which is exactly the state in
  which the switcher renders nothing.
- **An outstanding invitation and a redeemed one** ([M27](m27.md)), so the
  invitations page shows both halves of the lifecycle.
- **Notifications, some unread** ([M22](m22.md)), so the bell
  [M26.5](m26.5.md) added is not permanently empty.
- **Audit rows spanning several actions** ([M21](m21.md)), so `GET /api/v1/audit`
  returns a trail rather than one root-redirect change.
- **A blocked destination and a dispute in each state** — open, allowed,
  upheld ([M30](m30.md), [M31](m31.md)) — so the review queue can be looked at.
  The blocked attempt is seeded through the same service the product uses, so
  the stored URL is defanged the way a real one would be.
- **Bot blocking switched on for exactly one link** ([M32.5](m32.5.md)), so the
  setting is discoverable and its precedence is visible against links that
  inherit.

### What it must not do

- **No reputation feed is enabled, ever.** Feeds send destinations to a third
  party ([M32](m32.md)); a demo instance that quietly did that would be the
  worst possible violation of the promise the feature was built to qualify.
  Asserted by test.
- **No mailer is required.** The seeder runs on a default instance with no SMTP
  configured, and the invitation it creates is reachable by its copyable link
  (D1, D27). A demo that needed a relay would not run for most people.
- **`LINKCTRL_SIGNUP_MODE` is not changed.** The extra accounts are written by
  the seeder directly, not by opening registration — D7 says `closed` admits
  nobody by any path, and a seeder that flipped the mode to let itself in would
  be making that false to save itself a query.

### That it stays true

- **A test enumerates the features the demo is expected to show, and fails when
  one has no seeded rows.** The list is explicit and lives with the test, so
  extending it is a deliberate line in a later milestone's diff rather than
  something noticed by whoever next opens the demo. This is the mechanism; a
  note asking people to remember is not.

  The *rule* already exists — a milestone that adds something visible extends
  the seeder, inherited from
  [README.md](README.md#what-every-milestone-inherits) and checked by
  workflow.md's `Demo` gate since 2026-08-01. It landed before this milestone on
  purpose, because [M33](m33.md) sits in between and would otherwise ship in the
  window where the obligation exists and nothing enforces it. What M33.5 adds is
  the enforcement.
- `make demo-update` still refuses a dirty tree, still rebuilds from the commit
  just made, and remains **idempotent under `--reset`** — running it twice
  produces the same demo, which is what makes it safe to run at every milestone.
- The seeder's runtime does not grow enough to make `make demo-update`
  unpleasant at a milestone boundary. The figure is measured and recorded, not
  asserted.

## Deliberately not in this milestone

- **No new product behaviour.** Everything seeded already exists; if the demo
  cannot show a feature, that is a finding about the feature, not a licence to
  build a surface here.
- **No demo content for milestones after [M33](m33.md).** Routing rules, gated
  links, split tests, folders, custom domains, QR codes and webhooks are not yet
  built. The coverage list names the boundary rather than implying the demo is
  complete.
- **No second demo dataset.** The 100,000-link SLO dataset stays `lctl seed`'s
  job; conflating the two would make the demo unusable and the measurement
  unrepeatable.

## Risks

The coverage test is the interesting risk, and it cuts both ways. Without it the
demo silently rots again — which is precisely how this milestone came to exist.
With it, **every later milestone that ships a demo-visible feature inherits a
small obligation**: extend the seeder and the list, or the build fails. That is
a real tax on M34 through M44, and it is the point rather than a side effect. If
it proves too heavy the answer is to narrow what the list covers, deliberately
and in writing, not to delete the test.

The second risk is that seeded data is not real data. A dispute created by
insert has never been through the form that files one, and a demo that diverges
from what the product actually produces is worse than a thin demo. Seeding
through the service layer where one exists is the mitigation, and where a
milestone seeds around a service the file says which and why.

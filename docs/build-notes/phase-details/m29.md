# M29 — Self-serve signup, switchable at runtime

**Depends on:** [M26](m26.md) [M27](m27.md). **Discharges:** Collaboration scope
row *Self-serve signup, switchable at runtime by an owner*.

Ships after invitations so the toggle does what its label says: an owner enabling
sign-ups to add a colleague gets a colleague, not a stranger with a private
instance-within-the-instance.

## Done means

- A small `settings` table exists (decision recorded) holding the runtime signup
  mode.
- `LINKCTRL_SIGNUP_MODE` is a **ceiling, not a default**: the DB toggle chooses
  within it under `closed < invite < open`, and a test proves no session or API
  call can raise the effective mode above the environment's ceiling.
- **`open` requires a configured mailer** (decision D1): registration in open mode
  verifies the address before the account is usable, and with no mailer configured
  the effective ceiling is `invite`. That is stated in the UI beside the toggle,
  not discovered at signup time. Both behaviours tested.
- **`closed` admits no new account by any path** (decision D7), including invite
  redemption — see [M27](m27.md).
- The toggle is owner-only in UI and API, and **flipping it is an audit event**.
- Both the toggle and the signup form state what an account gets. Wording follows
  decision D6: a self-registered account gets its own organization and workspace;
  an invited one gets membership in the inviter's org and nothing else.
- A browser signup page exists and works without JavaScript. The alias is already
  reserved.
- `POST /api/v1/auth/register` honours the effective mode. Registration is
  rate-limited like login.
- The shipped ceiling default stays `closed`, and the docs say why.

## Risks

Open signup is the instance's largest abuse surface. Mailer-gated verification
(D1) is the mitigation; there is no CAPTCHA and the docs must not imply
otherwise.

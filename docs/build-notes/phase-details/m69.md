# M69 — The OIDC add-on: the foundation's acceptance test

**Depends on:** [M61](m61.md), [M63](m63.md), [M64](m64.md), [M65](m65.md);
[M68](m68.md) *(ordering preference — installing through the manager page is the
better proof, but [M67](m67.md)'s API and the M60 directory route suffice if it slips)*.
**Discharges:** the OIDC limb of Plan.md's *MFA, OAuth, OIDC, SSO, SCIM* row —
delivered as a first-party add-on rather than in core, the owner's structural
answer of 2026-08-18 — and the acceptance test the whole foundation was built
toward: *if the OIDC add-on cannot be built, the foundation is wrong.*

The code lives in `DevOfPie/LinkCtrl-OIDC` and is not this repository's to
milestone: the owner set its process as *the same gates, no phase loop* — CI
green, sabotage-verified tests, a changelog, a checksummed release. **This
milestone is the host-side half**: what this repository must prove about an
instance running that add-on, and the seam work the add-on's build surfaces.

## Done means

- **A stock instance signs a user in through OIDC** with the released add-on
  installed: discovery, authorization-code flow with PKCE against a real IdP
  implementation in CI (a containerized IdP, e.g. dex or Keycloak, in the
  integration compose — not a mock of the protocol), callback on the add-on's
  M64 route, assertion through M65, session minted by the host, provenance in
  the audit trail. Asserted by an integration test in **this** repository,
  because the claim is about the host.
- **Linking is exercised both ways**: a signed-in user connects the provider;
  an unlinked external subject is refused sign-in. The M65 boundary holds
  under a real protocol, not only under test modules.
- **The add-on consumes only the published SDK** at a tagged release —
  verified by its go.mod naming the SDK module at a version, no replace
  directive, no fork. The cross-repo contract phase-4-candidates.md calls the
  point of the exercise.
- **Its release is verifiable end to end**: checksummed artifact, published
  provenance (the owner's *both* answer — this is the provenance half M60
  deferred), and the checksum the manifest carries is what M60's loader
  verifies on install.
- **What the build discovered feeds back**: ABI gaps found while building the
  add-on land as normal findings — in-spec fixes in the milestone that owns
  the seam, or deferred rows. An ABI change it forces before 1.0 is a minor
  bump under M61's policy, exercised for real — the deprecation policy's
  first live case, if one arises.
- **The demo does not get OIDC**, deliberately: the demo instance has no IdP
  and a sign-in flow against a throwaway IdP demonstrates nothing a visitor
  can use. The manager page's demo coverage (M68's sample module) is where
  add-ons are visible in the demo; recorded here so the inherited demo rule's
  exception is stated rather than discovered.
- **`LinkCtrl-OIDC` carries an MIT `LICENSE` before this milestone is done**
  — owed-work #4, the owner's one-file act in the other repository, named
  here because it is an acceptance-test precondition: an unlicensed add-on
  repo means nobody may use the worked example this milestone exists to
  produce. This tree's part is only to check it and refuse to close while it
  is absent.
- **Docs say what shipped**: `docs/configuration.md` and `docs/SECURITY.md`
  cover running with the OIDC add-on — required-class default (M65), what the
  operator trusts (the IdP, the add-on's release checksum), what happens when
  the IdP is down (local sign-in unaffected).

## Risks

- Two repositories, one milestone: this repo's loop cannot commit the add-on's
  code, so the milestone can stall on work only the owner (or a session in the
  other checkout) can land. The dependency is named now; the mitigation is
  that every host-side limb is testable with the in-repo fixtures before the
  add-on's release exists, and the final integration proof is the last step,
  not the first.
- A containerized IdP in CI is new integration surface and a new flake source;
  pinning and health-gating it is part of the milestone, and the single-flake
  budget lesson (F256) applies.
- If the foundation is wrong, this is where it surfaces — by design. The
  phase's slack (planned 14 of 15) exists mostly for what this milestone
  finds.

# M50.5 — A logo in the middle of a QR code, and the first upload this product has

**Depends on:** [M50](m50.md), and the edge is **hard**. A logo is per-code
style, so it lands after the cardinality change rather than before it —
otherwise M50 retrofits logos onto a model that has just grown a dimension.
Transitively it needs [M49](m49.md), whose PNG renderer is what a raster logo
composites into.
**Discharges:** nothing on the scope tables. Owner-added scope, 2026-08-07. It
also makes the *logo reference* half of `00600_phase2_dormant.sql:59` true for
the first time — that comment has described the style blob as holding *"colours,
logo reference, error-correction level, margin, shape"* since Phase 1, and two
of the five have never existed.

**This is the first time anything in this product accepts a file.** That is the
milestone, and the QR compositing is the easy half. There is no `multipart`, no
`FormFile`, no `ParseMultipartForm` and no blob storage anywhere in the tree
today; every `bytea` column is key material or a hash. Everything below follows
from that rather than from QR codes.

## Done means

### The upload surface, which is new ground

- One upload endpoint, session-authenticated, behind the same permission that
  governs editing a link's QR style. A key may hold it or not per the inherited
  permission rule, and the milestone records which limb of D18 it matched.
- **Raster only. An SVG upload is refused.** An SVG is a document that can carry
  script and external references, and accepting one would mean either sanitising
  it or embedding untrusted markup inside an image this product serves. PNG and
  JPEG are decoded to pixels, which is a smaller thing to be wrong about.
- Bounded before it is decoded: a byte cap enforced on the request body, then a
  dimension cap enforced on the decoded image, then re-encoded to PNG by this
  product rather than stored as received. **Re-encoding is the point** — what
  gets served is bytes this product produced, so a crafted file cannot survive
  as itself.
- Content type is determined by sniffing the decoded result, never by the
  client's header or the filename.
- Each refusal is asserted by its own test, including a file whose extension and
  declared type disagree with its content.

### Where it is stored, decided here and recorded

The options are a `bytea` column, a filesystem path, and an object store. **The
milestone picks one and writes down why**, against three constraints this
product already has: `docker-compose.yml` mounts no volume for user content;
`make demo-update` regenerates the demo from nothing and must keep working; and
[M57](m57.md)'s conformance test asserts a single container with **no new
required dependency** — which an object store would be.

### Untrusted decode is a security surface, and gets a row

`docs/SECURITY.md` gains one. This product has never decoded user-supplied
binary, and image decoders are a classic source of memory-safety bugs. What the
row must state: the formats accepted, the caps, that decoding happens off the
redirect path, and that the stored artefact is re-encoded rather than
passed through. The decoders are standard library — `image/png` arrives with
[M49](m49.md) and `image/jpeg` with this milestone — so the dependency set does
not grow, which is the same argument D72 and M49 already ran.

### The code still scans, and that is a testable claim

- A logo occludes modules, so error correction is forced to **level H** whenever
  one is set, and the occluded area is capped as a fraction of the symbol.
  Both are asserted by test.
- **This reverses a decision [M49](m49.md) took.** M49 moved error-correction
  level out of the interface — *"the rest handled in the background"* — and a
  logo makes level load-bearing again. It stays out of the interface; the
  milestone chooses level H on the user's behalf when a logo is present, and
  says so on the page rather than offering a control.
- A decode test: every code the milestone renders with a logo is read back by a
  decoder and yields the original payload. A QR code that looks right and does
  not scan is the only failure mode that matters here.

### M49's claim survives, or this milestone does not ship

[M49](m49.md) asserts that an SVG at the set pixel size and the PNG describe the
same image, checked by walking the module grid. A logo composites into two
different renderers — embedded as a `data:` URI in the SVG, rasterised into the
PNG — so that claim gets harder rather than staying still.

- The same test is extended over the logo's bounding box: the grid check runs
  outside it, and the box itself is asserted to occupy the same modules in both
  outputs.
- `img-src 'self' data:` already permits the embedded form
  (`internal/httpx/middleware.go:271`), so no CSP waiver is needed. Asserted,
  because a milestone that quietly widened the CSP would be a security change
  wearing a QR milestone's clothes.

### It creates user content, so erasure has to reach it

This is the first thing in the product a person uploads, which gives
[M52](m52.md) a limb it does not currently have — that milestone's *what is
removed* list is foreign-key cascades only, and a stored file is not one.

- Deleting a link, a workspace or an organization removes its logos.
- M52's erasure sweep removes any that survive, and **M52's file is amended by
  this milestone rather than by M52 discovering the gap later**. That amendment
  is part of this milestone's definition of done, not a courtesy.

### Deliberately not done

- **No shapes, eye styles or gradients.** `00600:59`'s comment also promises
  *shape*; this milestone does not build it, and [M58](m58.md)'s sweep trues
  that word up rather than leaving one of the five promises outstanding.
- **No workspace logo library.** A logo belongs to the code that uses it. A
  reusable asset library is a second feature and a second surface.
- **No logo on the instance's own branding.** Unrelated, and nobody asked.

### Demo

`demoCoverage()` gains a row: one seeded code carries a logo, because a feature
whose entire output is visual shows nothing when the demo has none. The seeder
supplies its own image rather than depending on a file in the repository.

## Risks

**The highest in area F, and the risk is not the QR code.** Accepting a file is
a new class of surface in a product that has deliberately had none, and the
failure modes are the ones this repository has no experience of: a decoder bug,
a storage path that escapes its directory, a cap enforced after the allocation
it was meant to bound. The mitigations are all "do less" — raster only,
re-encode, cap twice, standard library decoders — and they are chosen for that
reason rather than for elegance.

The genuine unknown is storage. Every option costs something this product has so
far avoided: a `bytea` column puts binary in the row and in every backup, a
filesystem path needs a volume the compose file does not mount and that
`make demo-update` must not lose, and an object store is a required dependency
[M57](m57.md) has a test forbidding. The decision cannot be deferred into the
build, because it determines whether M57's conformance test still passes.

Second: this milestone took the phase from fifteen milestones to sixteen, past a
target the owner set on 2026-08-06. It is the first insertion the target has
been tested by, and the trap that rule warns about is fatter milestones rather
than more of them — so if this one turns out to be two, the answer is to say so
rather than to keep it whole for the sake of a number that has already moved.

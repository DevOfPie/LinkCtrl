# M24.5 — Dark mode

**Depends on:** nothing. The edge to [M25](m25.md) is an *ordering preference*:
this milestone's template scan becomes the enforcement for every later
milestone's UI, so it wants to land before the phase's UI-building run — M25,
M31, M37, M38, M41, M43, M44 — rather than restyle all of it afterwards.
**Discharges:** nothing on the scope tables. Owner-added scope, 2026-07-31,
after the plan was finalised; the why is in decisions.md. Also
[deferred-findings.md](../deferred-findings.md) F3 and F4, added on reopening.

The dashboard is light-only. This adds a dark theme that is correct by default
for a visitor who has expressed nothing, and explicit for one who has.

**Reopened 2026-07-31**, having been marked `done` while it did not work. The
theme rendered no differently in any browser: the light tokens were declared in
an unlayered `:root` and the dark tokens inside `@layer base`, and unlayered
declarations beat layered ones regardless of specificity. Rather than correct it
from a successor milestone and leave a `done` row asserting something false, the
row went back to `in progress` and the correction is part of this milestone. The
*Applied, not merely declared* section below is the amendment; everything above
it is as originally written and still holds.

## Done means

- With no stored preference, every dashboard page follows `prefers-color-scheme`.
  No account, cookie or JavaScript is involved on this path.
- An explicit override — system / light / dark — is settable from the dashboard,
  persisted in a cookie, and rendered as an attribute on `<html>` **by the
  server**. The initial response is already in the chosen theme, so there is no
  correcting script and no flash of the wrong theme to correct — the defect is
  unrepresentable rather than suppressed. Asserted by template test at all three
  cookie states.
- The override works without JavaScript (plain form POST), in the same
  progressive-enhancement idiom as [M38](m38.md)'s tree.
- The preference is per-browser by design, not a `users` column: it works on the
  login page, and two browsers on one account may disagree. Deliberate.
- Template colors move behind semantic theme tokens defined once in `input.css`.
  A test walks the embedded templates and **fails on any raw palette utility
  outside the token set** — the scan covers `fill-` and `stroke-` (the SVG
  charts) as well as `bg-`, `text-`, `border-` and `ring-`. That test, not
  review vigilance, is what holds every later milestone's UI to both themes.
- `color-scheme` is declared per theme, so native form controls and scrollbars
  follow without per-control styling.
- Every token pair meets WCAG AA contrast (4.5:1 for body text) in both themes,
  recorded next to the token definitions. **Where a pair cannot clear AA at
  today's light value, the light value moves** (decision D21) and the change is
  recorded beside those contrast figures. The dashboard's light appearance is
  therefore allowed to shift; an AA claim that exempts the theme already shipped
  would not be one.
- Deliberately not themed: `/docs` — the vendored, checksum-pinned Swagger UI
  stays light; transactional email ([M26](m26.md)); and any artifact a machine
  reads rather than a person — [M41](m41.md)'s QR codes stay dark-on-light in
  both themes, because the theme is chrome, never output.

## Applied, not merely declared

Added on reopening, 2026-07-31. The bullets above describe a theme that is
correct on paper; these are what make it correct in a browser.

- Light and dark token blocks sit in the **same cascade context**, so
  `:root[data-theme="dark"]` wins on specificity and source order rather than
  losing to an unlayered rule.
- `TestThemeTokensShareOneCascadeLayer` (new, `internal/ui`) parses the built
  `app.css`, finds every top-level construct declaring a `--t-*` token, and
  fails unless they all share one layer context. It must be **shown failing**
  against the stylesheet as first committed (`b289a39`) before it counts —
  demonstrated, not asserted.
- Every `--t-*` token in the light block has a counterpart in each dark block,
  asserted by that same test. One added to a single block is this defect's next
  version.
- Verified live against the composed stack: a dashboard page and the sign-in
  page are each fetched dark, light and with no cookie, and the **rendered token
  values differ** between them. Confirming the attribute was present is what let
  this ship broken, so presence of markup is no longer sufficient evidence.
- The contrast figures above are unchanged and not re-measured. They were
  computed correctly against token values this amendment does not alter — they
  were describing values no browser reached. Claiming fresh measurement would be
  false.

The **Appearance** control moves out of the footer, which is the one region a
person scanning for a setting does not read:

- It lives on the account page (`internal/ui/templates/pages/account.html`) —
  System, Light, Dark, still a plain form POST with no JavaScript.
- The sign-in page keeps its own control, from one shared partial. This is not
  redundancy: the per-browser design above rests on the preference being
  settable before there is an account, and account settings need a session.
- Exactly one control renders per page, asserted by template test across the
  eight pages, signed-in and signed-out.

## Risks

The sweep is wide but mechanical: every template is touched once to swap raw
palette classes for tokens, producing a diff review can only scan, not reason
about — the token test is what makes that sweep trustworthy. The genuine design
risk is the status palette: amber, rose and emerald drift out of AA contrast on
dark surfaces easily, which is why the contrast bullet is per token pair rather
than "looks fine".

The cascade fix is small and global: moving the token blocks changes which rules
win on every page at once, and getting it wrong inverts the themes rather than
failing loudly. That is why the test asserts the layer relationship directly
instead of trusting that one screenshot looks right. The control move touches
`layout.html`, which every page renders, and adds a render site on a page
reachable without a session — a control assuming account context will render
empty or panic exactly there, which is the page the second site exists for.

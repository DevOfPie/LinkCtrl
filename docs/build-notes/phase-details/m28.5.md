# M28.5 — Organization deletion and tenancy teardown

**Depends on:** [M28](m28.md). The edge is hard: deleting an organization means
deleting the memberships, workspaces and invitations M28 is what first lets a
person create.
**Discharges:** nothing on the scope tables. Owner-added scope, 2026-08-01,
placed when [M28](m28.md)'s audit bullet was found to require an operation the
product does not have. It also gives `org.delete` — seeded in Phase 1's
`00700_seed.sql` and granted to `owner` alone — the first operation it has ever
gated.

An organization is the one tenancy object with no way out. Every other object
this product creates can be removed by the person who made it; an organization
accumulates workspaces, links, members, invitations and audit history and then
stays forever. This milestone is the exit, and almost all of it is about what
deletion must *refuse* rather than what it removes.

## Done means

### The operation

- `DELETE /api/v1/organizations/{id}` and a UI path, gated by `org.delete` —
  its first enforcement. `org.delete` is held by the `owner` role only, and
  M28's rank rules already forbid an admin from acquiring it.
- Its API-key delegability is decided and recorded against
  [D18](../../../Plan.md#phase-2-decisions-taken-after-the-plan-was-finalised),
  naming which limb it matched or that it matched neither, per the inherited
  permission rule.
- Deletion is one transaction. A partially deleted organization is the one
  outcome worse than an undeletable one, because it leaves members resolving
  into workspaces that no longer exist — the state
  [D34](../../../Plan.md#phase-2-decisions-taken-after-the-plan-was-finalised)
  exists to prevent.

### What it refuses

Each refusal is asserted by its own test, and each names what an operator does
instead.

- **An organization still holding links** — refused, archived links included
  (**D37**, answered 2026-08-01, mirroring
  [D32](../../../Plan.md#phase-2-decisions-taken-after-the-plan-was-finalised)).
  An org-level cascade through the same links would make D32 bypassable by
  deleting one level up. The workspaces must be emptied first, and with no bulk
  delete until 2+ that is a link at a time — a cost this milestone states rather
  than hides.
- **The instance's last organization**, on the same reasoning that refuses the
  last owner and the last workspace: an instance with no organization has no
  path back that does not involve SQL.
- **It does *not* refuse on account of orphaned members.** See D36 below — that
  case was answered the other way, and it is what makes this milestone large.

### Belonging to nothing, which D36 makes a real state

Answered 2026-08-01, before code, as this file required. Deletion proceeds even
when a member has no other organization. Consequently:

- The account **survives** with no membership. Nothing deletes an account as a
  side effect of deleting an organization.
- `ResolveWorkspaceForUser` currently treats *no workspace* as a broken
  instance. It must treat it as an **empty state**, and every signed-in surface
  must render that state rather than erroring — asserted by test, not by
  clicking around. This is the session path
  [D31](../../../Plan.md#phase-2-decisions-taken-after-the-plan-was-finalised)
  deliberately left untouched during [M28](m28.md), so it is handled here with
  its own tests rather than as a side effect.
- On next sign-in the account is **prompted to create an organization**, and can
  take no other action until it has one — asserted by a test that signs in as an
  orphaned account and finds every other surface refused.
- **First-organization creation must be reachable by an account holding no
  permissions.** An account with no membership holds no role, so it holds no
  `orgs.create`, which
  [D16](../../../Plan.md#phase-2-decisions-taken-after-the-plan-was-finalised)
  grants through the `owner` role and which `POST /organizations` enforces
  today. The milestone **records which mechanism it used** and why that is not a
  second authorization axis — D16's rule is that the permission is a grant
  rather than a check on *how an account was made*, and a membership count is a
  check on present state. Getting this wrong is how RBAC quietly grows a
  parallel path, so it is named here rather than left to the build.

### What it leaves behind

- **Audit rows survive the organization they describe.** `organization.deleted`
  is emitted ([M21](m21.md)), and the trail for a deleted organization stays
  readable — a tenancy teardown that erased its own record is the one shape an
  audit log must not have. The retention rule stays [D5](../../../Plan.md#phase-2-decisions)'s.
- Whether anything else survives — the aliases, so they cannot be re-registered
  by somebody else, or nothing at all — is stated explicitly, with its reason.

### Enforcement

- The refusals are asserted by tests that fail when the guard is removed, not by
  review. Each guard locks the rows it counts before counting, the way M28's
  last-owner refusal does, so two administrators acting at once cannot each pass
  a check the other invalidates.
- `organization.deleted` joins `internal/audit`'s action vocabulary, and the
  comment at `audit.go` explaining why it was absent is removed rather than left
  to contradict the code beneath it.

## Deliberately not in this milestone

- **No soft delete, no restore, no trash.** Phase 1 has none for links and this
  is not the milestone that introduces the concept; deletion here is
  irreversible and says so in the confirmation surface.
- **No export before deletion.** Taking your data out is its own feature and
  belongs with bulk operations, which Plan.md already places in 2+.
- **No scheduled or delayed deletion.** A grace period is a state machine and a
  job, and both want a milestone that is about them.

## Risks

The central question is now answered (D36) and the answer is the expensive one,
which moves the risk rather than removing it. Most of this milestone is no
longer deletion at all — it is teaching the session path that *belongs to
nothing* is a state a signed-in person can legitimately be in. That path is
reached by every authenticated request, so a mistake there is an availability
bug for everyone rather than a bug in a teardown feature almost nobody runs.
The mitigation is that the new state is asserted by test at the session layer
and not merely rendered correctly on the page that prompts for an organization.

The second risk is the `orgs.create` seam. An account with no permissions being
offered a way to create something is exactly the shape that grows a second
authorization path beside RBAC, which is what D16 was written to prevent. The
milestone names its mechanism for a reason.

The second risk is that this milestone is the first to delete rows Phase 1's
schema only ever inserted, so the cascade behaviour in `00200_identity.sql` and
`00300_links.sql` is being exercised for the first time against real fixtures.
What the foreign keys actually do on delete is a tree fact to establish, early,
rather than an assumption to build on.
